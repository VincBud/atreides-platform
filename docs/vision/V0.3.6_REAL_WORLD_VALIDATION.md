# V0.3.6 — Real-World Validation & Signal Stack Freeze

**Status:** implemented · **Substep:** V0.3.6 of V0.3 · **Not production ready**

## Purpose

V0.3.0–V0.3.5 built a measurement stack: individual kinematics, ground-plane
calibration and its integrity monitoring, pairwise geometry, and spatial-cluster
dynamics. Every one of those milestones was verified against synthetic inputs
with known answers, which is the right way to check that a formula is correct.

It is not a way to find out what the stack does on real footage.

V0.3.6 answers that, reproducibly, and then freezes the scope. It adds **no**
behaviour, interaction or crowd feature, changes **no** detector or tracker
setting, and reaches **no** pass/fail conclusion.

### Why this milestone exists before any risk interpretation

A risk or decision layer would consume these signals and act on them. Before
that is worth building, three things have to be written down and measured rather
than assumed:

1. **How often each signal actually exists.** A risk rule reading "speed" needs
   to know that speed is absent for the first second of every track, and that
   every track fragmentation restarts that second.
2. **How stable the identities underneath the signals are.** Every signal is
   keyed on `(camera_id, track_id)`. If track IDs churn, the histories behind
   speed, pair proximity and cluster persistence all reset — and a rule
   reasoning about "this person over the last 10 seconds" would be reasoning
   about something that does not exist.
3. **Which numbers are measurements and which are proxies.** A future layer
   built on a proxy that was documented as ground truth would be wrong in a way
   nobody could see.

Building interpretation on top of an unmeasured stack means every later
surprise is ambiguous: is the rule wrong, or was the input never there? This
milestone removes that ambiguity before it can be introduced.

## Architecture

The harness is a **consumer** of the V0.3 runtime, never part of it.

```text
manifest
  → ValidationRunner       (composes the frozen pipeline, times it)
  → run artifacts          (tracked.mp4, three unsampled .jsonl.gz, run.json)
  → analysis pass          (streams each output back, one record at a time)
  → ClipValidationResult   (proxy metrics + manual ground truth, kept separate)
  → validation_summary.json / .csv / V0.3.6_REPORT.md
```

```text
services/vision/src/atreides_vision/validation/
├── manifest.py           # which clips, from which camera, of what kind
├── storage.py            # artifact layout + deterministic JSON/CSV/text writers
├── streams.py            # streaming JSONL reader (gzip transparent) + sizes
├── distributions.py      # one percentile implementation, shared by all metrics
├── track_metrics.py      # track presence, lifetime, occupancy, churn proxies
├── behavior_metrics.py   # signal coverage and warm-up
├── interaction_metrics.py# pair episodes, pair churn, track-churn propagation
├── crowd_metrics.py      # cluster occupancy, composition episodes, persistence
├── ground_truth.py       # manual annotation: templates, parsing, recall/precision
├── review_samples.py     # deterministic sample points, frame extraction, sheets
├── runner.py             # executes the frozen pipeline over a manifest
├── analysis.py           # run artifacts -> ClipValidationResult
├── models.py             # result types and their serialised shapes
└── reporting.py          # the three artifacts
```

Three boundaries are load-bearing:

**No measurement package imports the validation package.** The dependency runs
one way. Deleting `validation/` would leave behaviour, interaction, crowd and
calibration untouched.

**The runner composes; it does not measure.** It builds the same objects
`cli.py`'s `run` command builds and hands them to the same `VideoProcessor`. If
it re-implemented any part of the pipeline, validation would be measuring the
harness.

**The runner takes no threshold arguments at all.** Not "takes them and ignores
them" — there is no parameter to pass. A harness that accepted a confidence
override would eventually be used to tune against its own report.

## Validation inputs

A manifest, so footage can be added without touching validation logic:

```json
{
  "manifest_version": "0.3.6",
  "clips": [
    {
      "clip_id": "control_baseline_01",
      "input_path": "data/input/validation/control_baseline_01.mp4",
      "scene_type": "control",
      "camera_id": "val_control_01",
      "notes": "Elevated fixed camera, daylight, moderate occupancy."
    }
  ]
}
```

| Field | Required | Meaning |
| --- | --- | --- |
| `clip_id` | yes | Names the output directory. Unique; letters, digits, `_`, `-`, `.` only. |
| `input_path` | yes | Video file. Relative paths resolve against the working directory. Must exist at load time. |
| `scene_type` | yes | Free-form grouping label for the comparison table. Selects **no** behaviour and carries **no** thresholds. |
| `camera_id` | yes | The identity every output record is namespaced by. **Need not be unique across clips** — see below. |
| `notes` | no | Free text, reproduced in the report. |
| `calibration_path` | no | A **physically measured** ground-plane calibration. See "Physical validation" below. |

Three rules the loader enforces rather than trusts:

- **Clip IDs are unique.** They name directories; a duplicate would have one run
  overwrite another's artifacts.
- **Input files must exist before anything is processed.** A four-clip run that
  fails on the fourth after twenty minutes is a worse failure than one that
  never starts.
- **A clip's calibration must name the same camera the manifest does.** A
  mismatch means one of them describes different footage.

### Camera IDs deliberately repeat

**Several clips may share one `camera_id`, and that is the expected case.** A
real fixed camera produces many independent validation clips — different times
of day, different lighting, different crowd densities, different days, different
test scenarios. Forcing a fabricated distinct ID per clip would misdescribe the
deployment the harness exists to characterise.

Sharing a camera ID asserts exactly one thing: *these clips came from the same
physical camera*. It asserts **nothing** about identity across them, and the
harness never treats it as if it did:

| Boundary | Guarantee |
| --- | --- |
| Processing | Each clip gets its own detector, tracker, behaviour, interaction and crowd analyzers, constructed per clip. |
| Output | Each clip writes its own streams into its own `runs/<clip_id>/` directory. |
| Measurement | Each clip is measured by its own accumulators into its own `ClipValidationResult`. |
| Aggregation | Nothing merges, joins or compares track IDs across clips. |

So `camera_01/clip_A/track_7` and `camera_01/clip_B/track_7` are **two
independent tracklets that happen to share an integer**, exactly as
`cam_a/track_7` and `cam_b/track_7` are. Track identity does not survive a clip
boundary, and **no persistent identity is introduced by this milestone**.

The one consequence a reader must hold: **per-clip counts from clips sharing a
camera ID must not be added together.** Two clips of one camera reporting 40
unique track IDs each are not 80 people, or even 80 tracklets of one
continuously-observed scene. The summary emits a `clip_isolation` block naming
any camera with several clips, and the report states the rule where it applies.

This is covered by regression tests at three levels: the accumulator
(`camera_01/track_7` in two accumulators stays two tracklets), the runner (two
clips of one camera write separate artifacts and yield separate metrics), and
processing order (clip B measured after clip A equals clip B measured alone).

The committed manifest is [`config/validation/v0.3.6.json`](../../config/validation/v0.3.6.json).

## The two measurement classes

This is the distinction the whole milestone is organised around, and it is
enforced in the types, the JSON, the CSV columns and the report sections.

### A. Automated proxy / system metrics

Derived from Atreides' own output streams. No human is involved anywhere in the
derivation. They measure **what the system did**, not what was true in the room.

They serialise under `proxy_metrics`, with
`measurement_class: "automated_proxy_system_metrics"`, and every CSV column
carrying one is prefixed `proxy_`.

### B. Manual ground truth

Derived from human annotation only. They measure **what was actually there**.

They serialise under `manual_ground_truth`, with
`measurement_class: "manual_ground_truth"`, and every CSV column carrying one is
prefixed `manual_`.

**When no annotation exists, no manual metric is emitted at all** — not zero,
not null-that-plots-as-zero, absent. The status field reads `NOT_ANNOTATED` and
the report says so in words.

### The three claims a proxy metric can never make

| Proxy metric | Is **not** | Because |
| --- | --- | --- |
| `track_births_per_minute` | an ID-switch rate | A birth may be a person entering, a re-detection after occlusion, fragmentation, or a tracker lifecycle event. Nothing in the stream distinguishes them. |
| short-track fractions | proof of fragmentation | Equally consistent with somebody genuinely crossing a corner of the frame. |
| anything in this harness | detection recall | Recall needs a human counting the people actually visible. |

## Automated metric definitions

Every metric below is computed over the **unsampled** streams, which is why
validation runs never sample: a track present on frames 100–130 and sampled once
a second appears as one observation with a lifetime of zero.

### Track presence and lifetime

Reconstructed by grouping behaviour `observation` records on
`(camera_id, track_id)`.

| Metric | Unit | Definition |
| --- | --- | --- |
| `unique_track_ids` | count | Distinct `(camera_id, track_id)` pairs observed. **An upper bound on unique people, never a census.** |
| `track_lifetime_seconds` | s | `last_observed_timestamp − first_observed_timestamp`. A track seen on exactly one frame has a lifetime of **0.0 s** — deliberately not padded to a frame period, since padding would understate the short-track fractions. Reported as mean / median / P10 / P90 / min / max. |
| `observed_frames_per_track` | count | Frames a track was reported on, gaps excluded. |
| `active_tracks_per_frame` | count | Distinct tracks observed on each frame. **Frames the pipeline processed but which produced no observation count as zero**, so the mean is over the clip rather than conditioned on somebody being present. |
| `short_track_fractions` | fraction | Fraction of unique tracks with a lifetime below 0.5 s, 1.0 s and 2.0 s. Descriptive thresholds; **no acceptance meaning**. |
| `track_births_per_minute` | min⁻¹ | Track births ÷ minutes of processed source time. A birth is the first appearance of a `(camera_id, track_id)`. |
| `unique_track_ids_per_minute` | min⁻¹ | Identical arithmetic, reported alongside so a reader can see they are the same measurement asked two ways. |

### Observation gaps

A gap is the same track ID being reported, absent for one or more frames, then
reported again under **the same ID**. Gap duration is the elapsed source time
across the absence.

**A track lost and re-acquired under a new ID leaves no gap** — it leaves two
tracks. Nothing in this harness stitches them together, and no metric here
should be read as if it did.

Reported: tracks with at least one gap, total gap count, and the gap-duration
distribution (one entry per gap, not per track).

### Behaviour signal coverage

```text
coverage(signal) = observations containing that signal / total subject observations
```

The denominator includes observations carrying no signal at all — a freshly
acquired track has a position and no history, which is exactly what coverage
exists to quantify.

**An omitted signal means "not currently measurable", never "zero".** A subject
standing still still reports a speed of 0.0, so an absent speed is an absence of
measurement. Coverage counts presence in the record and never imputes a value.

Reported for `speed`, `acceleration`, `heading_change_rate` and
`stationary_duration`, with the raw counts alongside.

### Behaviour warm-up

Median seconds from a track's first observation to its first record carrying
each of `speed`, `acceleration` and `heading_change_rate`, over the tracks that
ever produced one. Tracks that never produced it are counted separately rather
than silently dropped from the median.

`stationary_duration` is excluded on purpose: it is emitted as soon as a subject
qualifies as stationary, so its "warm-up" would measure how long somebody moved
for, not how long the layer took.

**Track fragmentation restarts this clock.** That is the mechanism by which
upstream churn suppresses downstream signal availability, and it is why warm-up
sits next to the tracking proxies rather than in a section of its own.

#### What is deliberately not reported

`SubjectMotion` — the net displacement the interaction and crowd layers use for
relative heading — is **not serialised** by behaviour schema 0.3.3. It exists in
memory during a run and is consumed in process. There is therefore no honest
per-subject motion-heading coverage derivable from the streams, and the harness
does not invent one. The nearest available observables are
`heading_change_rate` coverage and the pairwise `relative_motion_heading`
availability.

### Interaction (pairwise) metrics

| Term | Definition |
| --- | --- |
| **pair reference** | A canonical `(camera_id, low_track_id, high_track_id)`. Two tracklets, not two people. |
| **pair episode** | A maximal run of consecutive frames in which that pair reference was measured. One pair reference can have several episodes — which is also how the interaction layer itself treats it, since proximity duration restarts. |

| Metric | Unit | Definition |
| --- | --- | --- |
| `pairs_per_frame` | count | Distinct pairs measured per processed frame; frames with none count as zero. Mean / median / max. |
| `unique_pair_references` | count | Distinct pair references over the clip. |
| `pair_episodes` | count | Episodes over the clip. |
| `pair_births_per_minute` | min⁻¹ | Episodes started ÷ minutes of processed source time. **Not a rate of social encounters.** |
| `pair_episode_seconds` | s | Episode duration distribution: median, P10, P90. |
| `short_episode_fraction` | fraction | Episodes shorter than 0.5 s. Descriptive. |

**Pair churn** is used in this document to mean exactly `pair_births_per_minute`
together with the episode-duration distribution. It is not used loosely anywhere
else.

#### Track churn propagating into pair history

The metric this section exists for. When a pair episode ends, **why** did it end?

An episode can end for exactly three reasons, and which are possible depends on
the analyser's `max_pair_distance`:

1. A member track **stopped existing** for the rest of the clip.
2. A member was **momentarily unobserved** and later returned under the same
   track ID — an observation gap, one layer downstream.
3. The two **separated past the distance gate** — *only when one is configured*.

```text
episodes_ending_with_member_track_end =
    pair episodes whose final frame is also the final frame
    one of their two member track IDs was ever observed on
```

Episodes still open when the clip ended are excluded from the denominator: they
have no ending to attribute.

**With `max_pair_distance = null` — the normalized-image default, and the mode
every current validation clip runs in — reason 3 cannot occur.** Every co-present
pair is measured at any separation, so pair-episode churn on these clips measures
*observation continuity* and nothing else. Two further consequences follow, and
the report states both:

- Pairs per frame is `N(N-1)/2` in the number of simultaneously tracked
  subjects. It is a combinatorial count, not a count of encounters.
- The pair-episode duration distribution is a distribution of uninterrupted
  co-observation, not of time spent together.

No identity stitching is attempted or implied. Knowing that a pair ended because
a track vanished says nothing about which later track, if any, is the same
person.

### Crowd / cluster metrics

V0.3.5 addresses a cluster by its **exact member set**. This section quantifies
what that costs.

| Term | Definition |
| --- | --- |
| **composition** | A canonical exact member set of camera-local track IDs. |
| **composition episode** | A maximal run of consecutive frames reporting that exact set as a cluster. |

| Metric | Unit | Definition |
| --- | --- | --- |
| `clusters_per_frame` | count | Clusters per processed frame; uncovered frames count as zero. Mean / max. |
| `clustered_subjects_per_frame` | count | Mean subjects inside a cluster. |
| `unclustered_subjects_per_frame` | count | Mean subjects in no cluster of the configured minimum size. |
| `largest_cluster_size` | count | Largest `member_count` observed. **Tracklets, not people.** |
| `cluster_size_histogram` | count | Cluster records by member count. |
| `unique_compositions` | count | Distinct member sets over the clip. |
| `composition_episodes` | count | Episodes over the clip. |
| `cluster_composition_births_per_minute` | min⁻¹ | Episodes started ÷ minutes of processed source time. |
| `composition_persistence_seconds` | s | The **analyser's own** `persistence_duration` at the end of each episode — not a validation-only recomputation. Median and P90. |
| `composition_survival_fractions` | fraction | Episodes whose persistence exceeded 1 s, 2 s and 5 s. A clip shorter than a threshold reports `null`, not `0.0`: it cannot answer that question, and a zero would read as an answer. |

A composition change is **not** automatically a real-world group event. It
occurs on a join, on a leave, when a member's track ID fragments and is
re-acquired under a new one, and when two members drift across the connectivity
radius and back.

#### Measured finding: exact-composition persistence is very short

**Median exact-composition persistence measured 0.00–0.16 s across the four
clips** — under a second on every scene type, and 0.00 s on the control scene.

**This is the metric behaving as specified, not a defect.** V0.3.5 addresses a
cluster by its *exact member set*, so any membership change ends the episode and
starts a new one. At the per-frame track churn these clips exhibit, the exact
member set of a real gathering changes almost every frame — one track
fragmenting, one re-acquired under a new ID, one drifting a few hundredths of a
normalized unit across the connectivity radius — even while the same people
stand in the same place.

What the figure does and does not measure:

- **It measures** the stability of an *exact composition*: how long one specific
  set of track IDs stayed mutually connected without a single membership change.
- **It does not measure** the continuity of a spatial crowd region. A cluster of
  roughly the same people, in roughly the same place, persisting for thirty
  seconds would still report a sequence of sub-second compositions.

**The V0.3.5 exact-member-set persistence algorithm was not changed by this
review**, and no conclusion is drawn from the finding here.

##### Bounded future review item

> **Evaluate whether a separate neutral spatial-cluster episode continuity
> primitive is needed after ground-truth review.**

Scoped deliberately narrowly:

- It is a **question to answer with evidence**, not a decision already taken.
- **Nothing has been implemented for it**, and nothing should be until the
  manual ground-truth review exists. Whether region continuity is worth
  measuring separately depends on how much of the observed churn is genuine
  movement versus tracking fragmentation, and only human annotation can separate
  those two.
- Any such primitive would remain **neutral and geometric**. It would measure
  region continuity, never social-group identity, membership or affiliation —
  the same boundary V0.3.5 holds.

### Output volume

| Metric | Definition |
| --- | --- |
| `size_bytes` | Size on disk **as stored**. The streams are gzipped, so this is the compressed size — what the file actually costs. Read from the filesystem, never by decoding. |
| `uncompressed_size_bytes` | Read from the gzip trailer (two seeks, no decompression pass). `null` for an uncompressed file, a multi-member archive, or a member over 4 GiB, where the trailer holds the length modulo 2³² and would report a confidently wrong number. |
| `record_count` | Lines in the stream, including its `run_metadata` header. |
| `records_per_source_second` | Records ÷ processed **source** seconds — not wall-clock seconds. |
| `structured_mib_per_source_minute` | Total structured bytes per source minute. Excludes the rendered review video, which is a review artifact rather than part of the machine-readable contract. |

### Performance

| Metric | Definition |
| --- | --- |
| `frames_processed` | Frames the pipeline actually processed. |
| `wall_clock_seconds` | Measured around `VideoProcessor.run`, **including annotated-video encoding**. |
| `processed_fps` | `frames_processed / wall_clock_seconds`. |
| `realtime_factor` | `processed_fps / source_fps`. Above 1.0 means faster than playback. |

**These are machine-specific development measurements.** They describe one
machine, one device backend, one build and this footage. They do **not**
establish production real-time capability, and two of them are only comparable
when their provenance records agree.

## Reproducibility

Every result carries the configuration that produced it, read off the
constructed objects rather than off intended values:

- detector and confidence
- tracker and every one of its thresholds
- deduplication state and rule name
- device
- coordinate space, distance unit, and whether it is physical
- behaviour / interaction / crowd analysis configuration
- output sampling (always `null` for validation)
- camera ID, input path, calibration path
- behaviour / interaction / crowd schema versions, package version
- `at_v021_defaults` — whether the run used the frozen defaults

The summary states `all_clips_at_v021_defaults` at the top level. When it is
false, the report says the cross-clip comparison is not valid.

All three artifacts are deterministic functions of the results: JSON with sorted
keys, CSV with a fixed column order, Markdown with fixed section order. Two runs
over the same inputs produce byte-identical reports, which makes `diff` between
two validation runs a usable tool.

## Runner usage

```bash
# Process every clip in the manifest, measure, and write all three artifacts.
uv run atreides-vision validation run \
  --manifest config/validation/v0.3.6.json \
  --output artifacts/v0.3.6-validation

# One scene only, without disturbing the others' artifacts.
uv run atreides-vision validation run \
  --manifest config/validation/v0.3.6.json \
  --output artifacts/v0.3.6-validation \
  --clip dense_venue_04

# A quick smoke run. The cap is recorded in every result, because a capped
# run's metrics are NOT comparable with a full one's.
uv run atreides-vision validation run \
  --manifest config/validation/v0.3.6.json \
  --output artifacts/v0.3.6-validation \
  --max-frames 200

# Regenerate every artifact from an existing run — no footage is re-processed.
# This is what picks up manual annotation added since the run.
uv run atreides-vision validation report \
  --manifest config/validation/v0.3.6.json \
  --output artifacts/v0.3.6-validation
```

Options: `--device`, `--max-frames`, `--sample-frames`, `--continuity-windows`,
`--continuity-window-seconds`, `--clip`, `--verbose`.

**There is no detector or tracker option.** Not one that is accepted and
ignored — there is no parameter to pass.

### Why two commands

Processing a clip costs minutes; reading its streams back costs seconds. The
split is what makes the annotation workflow practical:

1. `validation run` processes the clips and writes the annotation templates.
2. A human fills the templates in, over however long that takes.
3. `validation report` re-reads the same streams and the now-filled templates.

Both paths go through the same analysis module, so a regenerated report is
identical to a freshly-run one except for the ground-truth section. There is no
second implementation of any metric.

## Manual annotation

### The deterministic sample

Per clip, `validation run` generates 10 still frames and 3 continuity windows of
8 seconds (all configurable).

Sample points are a **pure function of frame count and frame rate** — no
randomness, no clock, no dependence on how the run went — so an annotation made
today still describes the frame a re-run produces next month.

Points sit at the midpoints of *n* equal slices, `(i + 0.5) / n` of the clip,
rather than at its start. Sampling the first seconds would measure the tracker's
warm-up and nothing else; sampling exact fractions would land on the first and
last frames, the two least representative frames in any clip.

Frames are extracted from the **rendered tracking video**, so boxes, track IDs,
confidences and trails are visible. Nothing new is drawn — the harness is a
consumer of the existing overlay, and a validation-only annotation layer would
mean reviewing something the production pipeline never emits. Frames are read
sequentially rather than by seeking, because seeking a compressed stream lands
on the nearest keyframe and would silently write a different frame than the plan
names.

### Frame annotation schema

`frame_annotations.csv`, pre-filled with the sample coordinates and blank
annotation columns:

```csv
clip_id,timestamp_seconds,frame_index,visible_people,correct_person_detections,false_positive_detections,missed_people,notes
```

Derived, over annotated rows only:

```text
detection_recall_sample = correct_person_detections / visible_people
precision_sample        = correct_person_detections / (correct + false_positive)
```

Neither is computed when its denominator is zero. Recall over zero visible
people is `null`, not `0.0` — recall of nothing is undefined, and a zero would
read as a total miss. A frame with false positives and no correct detections
yields a precision of `0.0`, which is a real measurement.

### Continuity annotation schema

`continuity_annotations.csv`:

```csv
clip_id,sequence_id,start_time,end_time,target_label,observed_track_ids,id_switch_count,fragment_count,lost_track_events,notes
```

`observed_track_ids` is a space- or semicolon-separated list. Commas are not a
separator — the file is CSV.

**`target_label` is run-local annotation, never an identity.** It is a scratch
label ("red jacket", "subject_a") for keeping one subject straight within one
window. Nothing reads it back into the pipeline, it is not stored against any
person, and it is **not ReID**. Two windows using the same label are not
asserting the same person.

### Parsing rules

- A **blank row** is an un-annotated row and contributes nothing.
- A **half-filled row** is rejected. Treating it as blank would drop the
  annotator's work; completing it would invent the rest.
- A **missing file** is a normal state (`NOT_ANNOTATED`), not an error.
- A file that **exists but does not parse** is an error. A malformed annotation
  silently skipped would understate exactly the metric it was written to supply.
- Negative counts, non-numeric counts, and rows claiming more correct detections
  than visible people are all rejected.
- **Existing annotation files are never overwritten** by a re-run.

### Status

| Status | Meaning |
| --- | --- |
| `NOT_ANNOTATED` | No rows filled in. **No** recall, precision or ID-switch figure is emitted. |
| `PARTIALLY_ANNOTATED` | Some rows filled in. Metrics are emitted over those rows only, with the sample size attached. |
| `ANNOTATED` | Every offered row filled in. |

## Physical validation — preparation only

**No current validation clip has a measured floor calibration.** All of them are
processed in normalized image units, and therefore:

- no metre, m/s or subjects/m² figure is derived for any of them;
- no floor dimension is estimated from doors, tiles, vehicles, or people in the
  footage;
- the report states the absence explicitly rather than omitting the subject.

Normalized image units are camera-local frame fractions. They are
resolution-independent, so the same scene gives the same numbers at 384×288 and
1920×1080 — but they are **not physical distance**, and two arbitrary cameras'
values are not comparable.

The path to a real physical validation is prepared and unused: add a manifest
entry with `calibration_path` pointing at a calibration whose correspondences
were **physically measured on the floor**. The runner then builds a
`GroundPlaneProjector` and the metric-threshold configurations, the streams
declare `is_physical: true`, and the report's unit caveats change accordingly —
with no change to any validation logic.

Until such a scene is supplied, no physical result exists to report, and none is
estimated.

## Multi-camera limitation

Each clip is its own camera. **Counts and identities are never combined across
cameras**, and nothing in this harness or in the codebase performs cross-camera
association.

The V1 product architecture places a further layer above this one:

```text
camera-local tracks → multi-camera association / fusion → temporary venue-local IDs
```

That layer is **not** part of V0.3.6 and is unbuilt — nothing here should be read
as evidence about it. There is no ReID, no appearance embedding and no face
recognition anywhere in this system; face recognition is excluded permanently,
while appearance-based ReID is primarily a V2 strengthening capability.

## Harness performance

Every input is streamed; no file is ever held in memory. Three structures scale
with content rather than with clip length, and are documented rather than
discovered later:

| Structure | Scales with |
| --- | --- |
| Track presence table | Unique track IDs in the clip. |
| Pair-episode durations | Pair episodes (one float each). |
| Composition-episode persistences + the distinct-composition set | Cluster composition episodes and distinct compositions. |

On the validation footage these are small. On hours of dense footage the
distinct-composition set would be the first to matter.

Per-frame occupancy is accumulated as a bounded histogram rather than a per-frame
list, so it costs nothing regardless of clip length.

## Validation status and freeze policy

**V0.3.6 does not establish that the V0.3 signal stack is sufficient, accurate
against reality, or valid in production.** It completes one review of several.

| Stage | Status |
| --- | --- |
| Implementation scope (V0.3.0 – V0.3.5 signals) | **complete** |
| Automated system / proxy validation on real footage | **complete** |
| Manual detection & tracking ground truth | **pending** |
| Controlled physical metric validation | **pending** |
| Production validation | **not established** |
| Final signal-stack acceptance / freeze | **pending the reviews above** |

What *is* settled is the **implementation scope**: no further measurement
feature should be added to V0.3.

What is **not** settled is whether these signals are accurate against reality,
whether their physical units mean anything on a real floor, and whether the
stack behaves acceptably in production. None of those can be answered by the
automated metrics here, which measure the system against itself.

**Detector and tracker defaults remain frozen at their V0.2.1 values for the
duration of validation.** They are not to be tuned in response to any figure in
this report — a stack tuned against its own validation output has not been
validated.

**Frozen during validation — do not change without a new milestone and a
re-validation:**

- RF-DETR Nano at confidence 0.30
- OC-SORT: high-confidence 0.30, minimum IoU 0.30, lost-track buffer 30,
  minimum consecutive frames 2, direction-consistency weight 0.2, `delta_t` 3
- Detection deduplication: Rule B3, enabled
- The individual, pairwise and crowd signal sets
- The three output schemas (behaviour 0.3.3, interaction 0.3.4, crowd 0.3.5)

**Not frozen:** the validation harness itself. Adding a clip, adding a metric
definition, or improving the report is expected and does not disturb the freeze,
because none of it can change what the pipeline produces.

### Known limitations of the implemented stack

1. **Camera-local track IDs are tracklets, not guaranteed unique people.**
   Occlusion fragments identity; when it does, behaviour history, pair history
   and exact cluster composition all reset.
2. **No physically validated metric output.** The projection is implemented and
   tested against synthetic cameras with known geometry; no real scene has been
   validated against measured floor distances.
3. **Camera-local only.** Each clip is measured independently: no association,
   no fusion, no venue-local identity, no ReID. Association and temporary
   venue-local identity are V1 capabilities not built at this milestone.
4. **Measurement only.** No risk engine, no decision engine, no classification
   of any behaviour, no operator alerting. The risk / decision-support
   foundation is V1 work that has not started.
5. **Detection is the floor for everything.** Missed detections in distant or
   dense regions propagate into every signal above them.
6. **No production readiness claim.** Development measurements on four clips,
   and production validation is not established.

### What V0.3.6 deliberately does not do

No risk score, threat score, aggression detection, fight detection, intoxication
detection, panic detection, crowd-danger classification, operator alert,
decision engine, LLM integration, ReID, appearance embedding, face recognition,
or cross-camera fusion. None of these exists in the codebase, and none was added.

There is also **no pass/fail verdict and no acceptance threshold** anywhere in
the harness or the report. The evidence does not support one, and a boolean
would be read as though it did. Where scenes differ, the difference is stated as
a ratio between measurements.
