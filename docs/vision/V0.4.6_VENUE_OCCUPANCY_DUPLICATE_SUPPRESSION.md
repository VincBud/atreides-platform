# V0.4.6 — Venue-level Occupancy & Duplicate Suppression

**Status:** implemented · **Engineering milestone:** V0.4.6 ·
**Product generation:** V1 · **Not production ready**

## Purpose

V0.4.4 wired association, fusion and venue-local temporary identity together into
`VenuePipeline`; V0.4.5 made that trail observable. Nothing before this milestone turned it
into a venue-level *count*. An operator watching a venue with overlapping camera coverage
still cannot answer "how many people are here right now" from that trail alone — the same
person seen by two cameras appears as two independent tracklets unless something above
association explicitly deduplicates them.

V0.4.6 is that something, and nothing more: a small, additive consumer that reads one venue
instant's observations and the identity registry that already exists, and produces a single,
truthful, auditable number — **current venue occupancy** — that suppresses a duplicate only
where association and fusion have already, confidently, said two camera-local tracklets are
one venue subject.

**V1 product claim:** Atreides V1 suppresses duplicate occupancy caused by overlapping camera
views when association evidence is sufficient, while explicitly preserving ambiguity when it
is not.

This is **not** cumulative unique-visitor counting, entry/exit accounting, or historical
footfall. It is a per-instant snapshot of who the system currently believes is present,
deduplicated by already-decided identity — nothing is counted across a session and nothing
here answers "how many different people visited today."

## The primary architecture question, and how it is resolved

The milestone's own framing warns against the naive answer: "how many `VenueSubject`s does
`VenueSubjectRegistry.active_subjects()` return" is **not** current occupancy. That count
includes provenance the registry is *retaining* — a subject whose last camera stopped
observing it thirty seconds ago is still `active_subjects()` until `retention_seconds`
elapses (V0.4.3a), because retention exists to let a momentary gap in one camera's view
resolve without losing the subject's identity. Retention is provenance bookkeeping; it is not
a claim that the person is standing there now.

The narrowest truthful signal for "currently present" already exists and needed no new
policy: **the set of `TrackObservation`s in one `VenueInstantResult.observations`.** That is
the same atomic, venue-time-aligned sampling unit V0.4.0 established as "now" for the whole
pipeline. A tracklet appears in occupancy for an instant if and only if it was actually
observed at that instant. No new timeout, presence window, or smoothing policy was invented
or is needed for this milestone — inventing one would be exactly the unjustified,
unvalidated threshold the milestone brief warns against introducing.

Consequently, "windowed" in the milestone's title resolves to: one venue instant *is* the
window. No multi-instant aggregation, smoothing or debouncing is introduced here; a caller
wanting a smoothed or session-level view must build that separately, on top of a sequence of
these per-instant snapshots — this milestone deliberately stops at one instant, matching
V0.4.5's own per-instant scope.

## Architectural position

```text
detection → camera-local tracking → calibration / spatial context
  → venue-time alignment / fan-in            (V0.4.0)
  → comparability gating + geometry          (V0.4.1)
  → deterministic association                (V0.4.2)
  → temporary venue-local identity           (V0.4.3a — identity/)
  → association → identity integration       (V0.4.3b — fusion/)
  → per-venue-instant runtime wiring         (V0.4.4 — venue_pipeline.py)
  → deterministic observability/reporting    (V0.4.5 — venue_pipeline_reporting.py)
  → current venue occupancy                  ← V0.4.6 builds this (occupancy/)
  → venue-level evidence → decision support  (later)
```

```text
services/vision/src/atreides_vision/occupancy/
├── __init__.py     # public surface
├── models.py       # OccupancyContribution, OccupancySnapshot — immutable, self-validating
├── analyzer.py      # compute_occupancy(result, registry) -> OccupancySnapshot
└── reporting.py     # OccupancyReportMetadata, occupancy_instant_record, JsonlOccupancyReportWriter
```

`occupancy` is a package, not a top-level module, because unlike `venue_pipeline_reporting`
it does not need the cross-cutting reach of `association` + `fusion` + `identity` +
`venue_pipeline` together — it reads only `association`'s observation/ordering vocabulary,
`identity`'s registry and venue-subject types, `behavior.models.SubjectRef`, and
`venue_pipeline`'s already-produced `VenueInstantResult`. **It never imports
`atreides_vision.fusion` at all** — a deliberately narrower reach than
`venue_pipeline_reporting.py` itself has: occupancy only ever reads fusion's *effect*, through
`VenueSubjectRegistry.owner_of()`, never fusion's own decision types. Enforced by
`test_occupancy_boundaries.py`, an AST-walked import guard following the pattern every
other layer's own boundary test already uses.

Occupancy does not:

- perform association or introduce a second matching/decision policy of its own;
- modify any `AssociationOutcome` or `IntegrationOutcome`, or fusion's confidence;
- mutate `VenueSubjectRegistry` membership, or merge two `VenueSubjectId`s;
- classify people, infer persistent identity, or replace `SubjectRef`;
- feed back into association, fusion or the registry — it is a terminal consumer;
- alter `VenuePipeline.process_instant`/`expire`, or V0.4.0's venue-time semantics.

`test_occupancy_boundaries.py` also pins that no signal layer (`tracking`, `detection`,
`behavior`, `interaction`, `crowd`, `zones`) imports `occupancy` back, and that
`venue_pipeline_reporting.py` does not import it either — the two reporting streams stay
independently evolving, per the observability decision below.

## Input contract

```python
def compute_occupancy(
    result: VenueInstantResult, registry: VenueSubjectRegistry
) -> OccupancySnapshot: ...
```

The narrowest safe input: one already-produced `VenueInstantResult` (V0.4.4) and the
`VenueSubjectRegistry` (V0.4.3a) that produced it — the exact same two things
`venue_pipeline_reporting.instant_record` already reads. Occupancy has no dependency on
V0.4.5's JSONL schema or on any reporting output; a caller can compute occupancy from a live
`VenuePipeline` run without ever writing a report line.

## Duplicate-suppression algorithm

For every `TrackObservation` in `result.observations`:

1. Compute its tracklet key with `identity.models.tracklet_key(observation.subject,
   observation.stream)` — the same two-argument key fusion's own `integrate_round` uses.
2. Ask `registry.owner_of(key)` who currently claims it.
3. `None` → the tracklet is **unresolved**: no positive association/fusion decision claims
   it, so it counts independently, exactly once.
4. A `VenueSubjectId` → group every observed tracklet by that owner. A group of *N*
   currently-observed tracklets sharing one live owner contributes **1** to occupancy and
   **N − 1** to `suppressed_duplicate_count`.

`registry.owner_of()` reflects only an already-applied, positive integration outcome
(`fusion.integration.IntegrationOutcome.APPLIED`). This makes every non-positive
`AssociationOutcome` (`AMBIGUOUS`, `UNASSOCIATED`, `NOT_COMPARABLE`) and every non-`APPLIED`
`IntegrationOutcome` (including `REFUSED`) automatically incapable of causing a suppression:
occupancy re-derives nothing association or fusion already declined to decide, and never
invents a merge to make a count tidier. A `REFUSED` cross-subject conflict leaves both
`VenueSubjectId`s distinct and each contributes independently, per its own currently-observed
membership — never merged, never one of them silently dropped.

Members within a contribution, and unresolved tracklets, are sorted by
`association.observation_order_key` before their `SubjectRef` is extracted, and contributing
subjects are ordered by their own canonical `VenueSubjectId` order — the result is
independent of the order `result.observations` happened to be iterated or produced in.

## Domain model

```python
@dataclass(frozen=True, slots=True)
class OccupancyContribution:
    subject_id: VenueSubjectId
    members: tuple[SubjectRef, ...]  # currently observed tracklets only

    @property
    def suppressed_count(self) -> int: ...  # len(members) - 1
    def to_record(self) -> dict[str, Any]: ...


@dataclass(frozen=True, slots=True)
class OccupancySnapshot:
    venue_seconds: float
    raw_active_track_count: int
    contributing_subjects: tuple[OccupancyContribution, ...]
    unresolved_tracklets: tuple[SubjectRef, ...]

    @property
    def active_venue_subject_count(self) -> int: ...  # len(contributing_subjects)
    @property
    def occupancy_count(self) -> int: ...  # active_venue_subject_count + len(unresolved_tracklets)
    @property
    def suppressed_duplicate_count(self) -> int: ...  # sum of every contribution's suppressed_count
    def to_record(self) -> dict[str, Any]: ...
```

Both types are immutable and self-validating: `__post_init__` raises `OccupancyError` for
every internal contradiction a caller could otherwise construct — an empty contribution, a
duplicated member, contributing subjects out of canonical order, the same subject
contributing twice, a tracklet claimed by two contributions, a tracklet that is both a member
and unresolved, or a `raw_active_track_count` that does not reconcile with the distinct
tracklets actually accounted for. Field names state exactly what they mean:
`raw_active_track_count` is the raw count before suppression, `occupancy_count` is the
truthful "how many people does this instant currently represent" figure, and
`suppressed_duplicate_count` is the number of tracklets folded into a contributing subject's
first member. Nothing is named as if it were a stronger claim than it is — no field is called
"visitors," "unique people," or "headcount."

### Arithmetic invariant

```
raw_active_track_count == occupancy_count + suppressed_duplicate_count
```

Enforced at construction, and directly exercised by the milestone's own worked example: raw
= 50 (18 + 15 + 17 tracklets across three cameras), six tracklets suppressed by confirmed
fusion into three-member and two-member subjects, giving `occupancy_count = 44`. If the same
scenario were ambiguous instead of confirmed, no suppression happens and `occupancy_count`
stays 50 — pinned by `test_occupancy_analyzer.py`'s ambiguous/unassociated/not-comparable/
refused scenarios.

## Active-vs-historical membership

A contributing subject's `members` are **only** the tracklets actually present in the current
instant's observations — never the subject's full historical `VenueSubject.members` from the
registry. If one camera's stream stops producing frames for a subject that is still being
observed by another camera, the next instant's occupancy shows that subject contributing only
its still-observed member, with `suppressed_count` dropping to 0 — the historical, no-longer-
observed tracklet never inflates or distorts the current count. If every camera stops
observing a subject for one instant, that subject contributes nothing to that instant's
occupancy at all, even though `registry.active_subjects()` still lists it as retained
provenance. Registry retention is not, and is never treated as, current presence. Pinned by
`TestActiveVersusHistoricalMembership` in `test_occupancy_analyzer.py`.

## Lifecycle and venue time

Occupancy performs no lifecycle management of its own — `VenuePipeline.expire()` (delegating
to `VenueSubjectRegistry.expire()`, V0.4.3a) is the only retirement policy, unchanged. Once a
subject is retired, `registry.owner_of()` no longer resolves any of its former tracklet keys
(`VenueSubjectRegistry.retire()` already pops them from its internal claims), so a tracklet
that reappears afterward is unresolved rather than silently reattributed to a retired
identity. Occupancy is computed strictly from venue-time-ordered instants; no wall-clock time
enters anywhere in this milestone. Pinned by `TestLifecycleAndExpiry`.

## Single-camera behavior

A single-camera session takes the same path as any other, with no special case: every
candidate pair is `NOT_COMPARABLE`, fusion never applies anything, `registry.owner_of()`
never resolves, so every tracklet is unresolved and counts independently —
`occupancy_count == raw_active_track_count` and `suppressed_duplicate_count == 0`, exactly as
V0.4.4's own single-camera path already establishes for association and fusion. Pinned by
`TestSingleCameraIsAValidRuntimePath`.

## Determinism

Same input, same output, byte-for-byte, independent of camera or observation enumeration
order. `compute_occupancy` performs no iteration over an unordered collection without first
sorting by an already-established canonical key (`observation_order_key` for tracklets,
`VenueSubjectId`'s own `order=True` comparison for contributing subjects) — association order
never depends on camera enumeration order. Pinned by `TestDeterminism` in both
`test_occupancy_analyzer.py` (two independent runs, and every permutation of one scenario's
observation ordering) and `test_occupancy_reporting.py` (the same, at the record level).
Repeated computation over the same `(result, registry)` state is idempotent and mutates
neither.

## Observability integration

`occupancy/reporting.py` is a **separate, additive JSONL stream** (`OCCUPANCY_REPORT_SCHEMA_VERSION
= "0.4.6"`), not a change to V0.4.5's `venue_pipeline_reporting` schema. V0.4.5's schema is a
frozen, versioned contract a downstream reader may already depend on; adding an `occupancy`
field to it would couple two independently evolving concerns — the association/fusion/identity
trail and this milestone's derived count — into one schema version. A separate stream keeps
each independently versioned and independently readable, and is enforced structurally:
`venue_pipeline_reporting.py` does not import `occupancy`, pinned by
`test_venue_pipeline_reporting_does_not_import_occupancy`.

```python
OCCUPANCY_REPORT_SCHEMA_VERSION = "0.4.6"

@dataclass(frozen=True, slots=True)
class OccupancyReportMetadata:
    session_id: str
    def to_record(self) -> dict[str, Any]: ...

def occupancy_instant_record(snapshot: OccupancySnapshot, session_id: str) -> dict[str, Any]: ...

class JsonlOccupancyReportWriter:
    def __init__(self, path: Path | str, metadata: OccupancyReportMetadata, compress: bool | None = None) -> None: ...
    @property
    def path(self) -> Path: ...
    @property
    def metadata(self) -> OccupancyReportMetadata: ...
    @property
    def snapshots_written(self) -> int: ...
    @property
    def is_compressed(self) -> bool: ...
    def write_snapshot(self, snapshot: OccupancySnapshot) -> None: ...
    def release(self) -> None: ...
    def __enter__(self) -> Self: ...
    def __exit__(self, ...) -> None: ...
```

One JSON object per line: a header (`record_type: "occupancy_report"`) followed by one
`record_type: "occupancy_instant"` line per `write_snapshot` call, each repeating
`schema_version` and `session_id`. `occupancy_instant_record` delegates every substantive
field to `OccupancySnapshot.to_record()` — this module invents no second representation of
the snapshot's own data. Enabling or disabling occupancy reporting changes nothing about
`VenuePipeline`, `AssociationEngine` or `VenueSubjectRegistry` state; a caller can compute and
report occupancy, or skip it entirely, with the runtime pipeline behaving identically either
way. Pinned by `TestReportingNeverMutatesRuntimeState` and `TestOccupancyNeverMutatesRuntimeState`.

## Failure semantics

An invalid `OccupancySnapshot`/`OccupancyContribution` never constructs — every invariant
violation raises `OccupancyError` at construction, immediately and explicitly. A reporting
failure (unwritable destination, write after `release()`) also raises `OccupancyError`, never
masked as `occupancy_count == 0` or silently swallowed. A legal edge case — zero observations,
a single lone tracklet, a fully single-camera instant — always produces a valid,
fully-reconciled snapshot; there is no "unknown occupancy" sentinel because the underlying
input (one venue instant's observations) is always well-formed by the time it reaches this
module.

## What V0.4.6 does not do

- **No cumulative unique-visitor counting, entry/exit accounting, or historical footfall.**
  Every snapshot describes exactly one venue instant; nothing here counts across a session.
- **No persistent identity, ReID, appearance embeddings, or biometric identity of any kind.**
- **No automatic merge of two already-distinct `VenueSubjectId`s.** A `REFUSED` fusion outcome
  stays refused; occupancy never reconciles it to make a count tidier.
- **No occupancy forecasting, capacity alerting, dashboard, or customer-facing API.**
- **No Risk/Decision Engine, behavior/crowd risk scoring, or new association/confidence
  policy.** Every suppression decision made here was already decided by V0.4.2/V0.4.3b.
- **No new presence timeout, window or smoothing policy.** One venue instant is the window.
- **No CLI wiring.** No command in `cli.py` was added or changed.
- **No modification of `venue_pipeline.py` or `venue_pipeline_reporting.py`.** Both are
  byte-for-byte unchanged by this milestone.

## Validation

**Synthetic only.** Every behaviour in this milestone is established by unit tests built from
realistic synthetic runtime sequences — `VenuePipeline` driven through a sequence of venue
instants exactly as `test_venue_pipeline.py` (V0.4.4) already does — rather than by
constructing a final `OccupancySnapshot` directly, except where the domain's own arithmetic
invariant is being tested in isolation (`test_occupancy_models.py`). This proves the
suppression contract; it says nothing about occlusion, crowding, real multi-camera footage,
or a real venue — the same limitation every milestone in this chain already carries.

- Human-verified ground truth: **`NOT_ANNOTATED`.**
- Proxy/system metrics: **none emitted beyond the snapshot's own fields.** This milestone

## Known limitations

- **No real-world validation whatsoever**, inherited unchanged from V0.4.1–V0.4.5: every
  threshold this snapshot reflects is a development default or an unmeasured design choice
  from association/fusion, not a new one introduced here.
- **No aggregation across instants.** Each snapshot describes exactly one venue instant; a
  reader wanting a smoothed, debounced, or session-level occupancy view must build that
  separately — this milestone deliberately does not do that aggregation, matching V0.4.5's
  own per-instant scope.
- **No consumer wired in `cli.py`.** No command in this repository currently produces this
  stream from a real run; it is available to be called from a future orchestration point,
  exactly as V0.4.5 already noted for itself.
- **Case-4 cross-subject conflict (V0.4.3b) remains unresolved.** A `REFUSED` outcome still
  leaves two distinct venue subjects both contributing to occupancy independently; if they
  are in fact the same person, occupancy over-counts by exactly the same amount fusion itself
  already declined to reconcile — this is the visible, honest cost of preferring a missed
  association over a wrong merge, not a defect introduced by this milestone.
- **Caller must compute occupancy promptly after `process_instant`**, before any further
  `expire()` call retires a subject that instant's observations still describe — the same
  caveat V0.4.5 already documents for its own reporting call.

## Next architectural seam

The next seam is a real caller of this snapshot: wiring `compute_occupancy` and
`JsonlOccupancyReportWriter` into an actual multi-camera run, and — as a distinct,

first, human-visible decision-support surface for the number this milestone now makes
