# V0.4.4 — Multi-Camera Association/Fusion Pipeline Wiring

**Status:** implemented · **Engineering milestone:** V0.4.4 ·
**Product generation:** V1 · **Not production ready**

## Purpose

V0.4.2 built the association engine. V0.4.3a/b built venue-local identity and the
integration seam between association and identity. Until this milestone, nothing called
them together: each was fully implemented and exhaustively tested in isolation, with no
runtime object owning one `AssociationEngine` and one `VenueSubjectRegistry` for a session
and driving them through the sequence each already documents as its own contract.

V0.4.4 is that runtime seam, and nothing more:

```text
camera-local observations, already venue-time aligned and projected
  -> AssociationEngine.observe(venue_seconds, observations)   (V0.4.2, unchanged)
  -> AssociationRound
  -> fusion.integrate_round(registry, round_)                 (V0.4.3b, unchanged)
  -> VenueSubjectRegistry mutated only through that call        (V0.4.3a, unchanged)
  -> VenueInstantResult                                        <- V0.4.4 builds this
```

It introduces no new association intelligence, no new fusion policy, no new identity
invariant, and no occupancy, reporting, risk, or decision-support behaviour. It is the
smallest object that can own the two collaborators' state for one venue session and call
each of them exactly once per venue instant, in the right order.

## Architectural position

```text
detection → camera-local tracking → calibration / spatial context
  → venue-time alignment / fan-in            (V0.4.0)
  → comparability gating + geometry          (V0.4.1)
  → deterministic association                (V0.4.2)
  → temporary venue-local identity           (V0.4.3a — identity/)
  → association → identity integration       (V0.4.3b — fusion/)
  → per-venue-instant runtime wiring         ← V0.4.4 builds this (venue_pipeline.py)
  → venue-level evidence → decision support  (later)
```

```text
services/vision/src/atreides_vision/
└── venue_pipeline.py     # V0.4.4 — VenuePipeline, VenueInstantResult
```

`venue_pipeline.py` is a single top-level module, not a package, deliberately placed
alongside `identity/`, `association/` and `fusion/` rather than inside any of them: each of
those packages' own boundary guard already forbids the cross-cutting reach this
orchestration needs (`association` cannot see `identity`; `identity` cannot see
`association`; `venue` cannot see any of the three). `fusion` is the one existing package
already permitted to see both `association` and `identity` — this module reaches the same
three packages `fusion` does, plus `fusion` itself, and nothing further. Enforced by
`test_venue_pipeline_boundaries.py`, an AST-walked import guard following the same pattern
as `test_fusion_boundaries.py`.

It does **not** import `atreides_vision.venue` or `atreides_vision.video`. This milestone
wires already-built `TrackObservation` values into association and fusion; it does not
derive them from raw frames, pixels, or camera-local tracks. Projecting a camera-local
track into a venue-time-aligned, spatially-contextualised `TrackObservation` needs
calibration and projector access this milestone does not own — inventing missing timing
confidence, calibration trust, or spatial context here would be exactly the kind of silent
fabrication the association gates exist to refuse. Building an observation remains the
caller's responsibility; this pipeline's contract begins at the observation.

## Public surface

```python
class VenuePipeline:
    def __init__(
        self,
        *,
        gating: AssociationGatingConfig | None = None,
        decisions: AssociationDecisionConfig | None = None,
        identity: VenueIdentityConfig | None = None,
    ) -> None: ...

    @property
    def registry(self) -> VenueSubjectRegistry: ...

    @property
    def tracked_pairs(self) -> int: ...

    def process_instant(
        self, venue_seconds: float, observations: Iterable[TrackObservation]
    ) -> VenueInstantResult: ...

    def expire(self, now_seconds: float) -> tuple[VenueSubjectId, ...]: ...


@dataclass(frozen=True, slots=True)
class VenueInstantResult:
    venue_seconds: float
    observations: tuple[TrackObservation, ...]
    round: AssociationRound
    integration: IntegrationResult
    active_subjects: tuple[VenueSubjectId, ...]
```

That is the entire surface this milestone adds. `VenuePipeline` owns exactly one
`AssociationEngine` and one `VenueSubjectRegistry` for its lifetime (`__slots__ = ("_engine",
"_registry")`) — one instance is one venue session, and nothing here is global or shared
between instances.

## Execution flow

`process_instant(venue_seconds, observations)` calls `AssociationEngine.observe` exactly
once, then `fusion.integrate_round` exactly once, in that order, and returns a
`VenueInstantResult` built from both plus a fresh read of `registry.active_subjects()`:

```python
round_ = self._engine.observe(venue_seconds, observations)
integration = integrate_round(self._registry, round_)
return VenueInstantResult(
    venue_seconds=venue_seconds,
    observations=round_.observations,
    round=round_,
    integration=integration,
    active_subjects=self._registry.active_subjects(),
)
```

No third call is made. No result is filtered: an empty `AssociationRound`, an
`IntegrationResult` with only `IGNORED`/`REFUSED` outcomes, and an unchanged
`active_subjects` tuple are all valid, fully-populated `VenueInstantResult`s — "nothing
happened this instant" is as inspectable as "a venue subject was created", matching the
completeness both `AssociationRound` and `IntegrationResult` already guarantee on their own.

## State ownership

- **`AssociationEngine`** owns all cross-instant, per-candidate-pair evidence
  (`tracked_pairs`, `_last_seconds`). V0.4.4 does not read or duplicate this state; it is
  reached only through `observe()`.
- **`VenueSubjectRegistry`** owns all venue-local identity state. `VenuePipeline.registry`
  returns the live registry object itself, not a copy, so a caller can use its full existing
  read surface (`get`, `subjects`, `active_subjects`, `owner_of`, `provenance_for`) between
  calls to `process_instant`. Every mutation still happens only through `integrate_round`
  (inside `process_instant`) or `expire` — `VenuePipeline` performs no direct registry
  mutation of its own.
- **`VenuePipeline`** itself holds no additional state beyond its two collaborators. It
  computes nothing, decides nothing, and stores no history across instants.

## Observation ingestion and adaptation

None is performed. `process_instant` accepts `Iterable[TrackObservation]` — the same,
unmodified V0.4.1/V0.4.2 type — and passes it straight to `AssociationEngine.observe`.
There is no adapter, no camera-local-track-to-observation conversion, and no calibration or
projector access anywhere in this module. A future milestone that owns projector access is
expected to sit above this one and produce the `TrackObservation`s this pipeline consumes;
V0.4.4 deliberately does not reach for that responsibility.

## Ordering semantics

`process_instant`'s result is independent of the order `observations` is iterated in.
`AssociationEngine.observe` already sorts by `observation_order_key` and rejects a
duplicate tracklet within one instant (`AssociationError`, unchanged from V0.4.2);
`integrate_round` already processes `round_.decisions` in their canonical `CandidateKey`
order (unchanged from V0.4.3b). V0.4.4 introduces no further canonicalisation and no
further ordering dependency — it only calls each layer once, using each layer's own
already-established canonical order. Pinned by
`TestDeterminismAcrossOrderingAndReplay.test_observation_enumeration_order_within_an_instant_changes_nothing`,
which sweeps every permutation of a four-observation instant and asserts an identical
`AssociationRound.to_record()` and identical `active_subjects` for every ordering.

## Lifecycle and expiry

`VenuePipeline.expire(now_seconds)` is a thin delegation to
`VenueSubjectRegistry.expire(now_seconds)` — the same two-pass, venue-time-only lifecycle
policy V0.4.3a already implements (idle subjects retired past `idle_expiry_seconds`,
retired subjects purged past `retention_seconds`). V0.4.4 adds no second expiry policy and
introduces no new configuration.

Critically, `process_instant` **never calls `expire` implicitly**. Lifecycle advancement is
entirely caller-driven: a caller decides when to call `expire` (for example, once per
processed instant, using that instant's own `venue_seconds`), and an instant's own
membership changes are never retired by the same call that produced them. This matches
V0.4.3a's own stated caller-driven expiry contract; V0.4.4 does not change it.

## Single-camera behavior

A single-camera session takes exactly the same path as any other. With one camera, every
candidate pair the engine considers is same-camera and every decision resolves to
`NOT_COMPARABLE` (V0.4.1's own hard gate); `integrate_round` records each as `IGNORED`; the
registry never gains a member. This is the existing multi-camera path taking zero eligible
decisions — not a special mode, not an error, not a degenerate crash. Pinned by
`TestSingleCameraIsAValidRuntimePath`.

## Zero-frame and ended-stream behavior

An empty `observations` iterable is a legal, idempotent no-op instant: an `AssociationRound`
with no observations and no decisions, an `IntegrationResult` with no outcomes, and
`active_subjects` unchanged — exactly what a stream that has not started decoding yet, or
has already ended, produces. A stream ending mid-session (one camera stops contributing
observations while others continue) is handled the same way at every later instant: the
engine simply receives fewer observations, and any venue subject that already claimed that
camera's tracklet keeps that membership until it is explicitly removed or the subject is
retired — `process_instant` performs no automatic membership removal on a stream's absence,
since "no observation this instant" is not evidence that the tracklet's claim on identity
was wrong. Pinned by `TestZeroFrameAndEndedStreams`.

## Failure and refusal semantics

`process_instant` introduces no new error type. `AssociationError`, `FusionError`, and
`IdentityError` all propagate unchanged from the layer that raises them:

- `AssociationError` — venue_seconds fails to strictly advance past the pipeline's last
  processed instant, or a tracklet appears twice within one instant (both structural
  violations of `AssociationEngine.observe`'s own contract).
- `FusionError` — propagated unchanged from `integrate_round` (in practice, only reachable
  through a `MembershipOutcome` invariant violation, since `integrate_round` never invents
  new failure modes of its own).
- `IdentityError` — propagated unchanged for registry precondition violations
  `integrate_round` does not model as a refusal outcome (registry at capacity, venue time
  moving backwards for a subject fusion is not currently reconciling).

`AssociationOutcome.AMBIGUOUS`, `UNASSOCIATED`, and `NOT_COMPARABLE`, and
`IntegrationOutcome.REFUSED` and `IGNORED`, are never converted into exceptions anywhere in
this module — they remain first-class, non-mutating, reported outcomes exactly as V0.4.2 and
V0.4.3b already established. `VenuePipeline` neither forces a merge nor silently drops a
refusal; every outcome is visible in the returned `VenueInstantResult`. Pinned by
`TestNonPositiveOutcomesNeverMutateIdentity`,
`TestDistinctVenueSubjectsAreNeverAutoMerged`, and
`TestSameCameraExclusivityAtVenueLevel`.

## Determinism

Same input, same output, byte-for-byte: two independent runs of the same sequence of
`process_instant` calls produce identical `AssociationRound.to_record()` output and
identical `active_subjects` tuples at every instant, and results never depend on
observation enumeration order within an instant. Pinned by
`TestDeterminismAcrossOrderingAndReplay`.

## Idempotency

Reprocessing is not something `VenuePipeline` performs on its own — venue_seconds must
still strictly advance, matching `AssociationEngine`'s own contract — but continuing to
observe an already-associated pair produces only `NO_OP`/`APPLIED`
`IntegrationOutcome`s at every later instant, never a duplicate venue subject, exactly as
`integrate_round`'s own idempotency guarantee already establishes. Pinned by
`TestRepeatedProcessingIsIdempotent`.

## What V0.4.4 does not do

- **No occupancy, no duplicate-suppression product metric, no cumulative unique-visitor
  count.** A venue subject existing does not yet feed any headcount.
- **No JSONL/reporting schema, no `schema_version`, no dashboard.** Nothing in this
  milestone writes a report.
- **No risk or decision engine, no decision-support output.**
- **No venue-level behaviour/crowd/interaction fusion.** Those layers remain camera-local.
- **No automatic merge of two already-distinct venue subjects.** V0.4.3b's case-4 refusal
  is unchanged and unresolved by this milestone.
- **No new association intelligence, no new fusion policy, no new identity invariant.**
  Every gate, matching rule, and reconciliation rule this milestone relies on already
  existed in V0.4.1–V0.4.3 and is called, not reimplemented.
- **No observation ingestion or adaptation from raw frames, camera-local tracks, or
  calibration.** `TrackObservation` construction remains entirely the caller's
  responsibility.
- **No implicit `expire()` call inside `process_instant`.** Lifecycle advancement stays
  fully caller-driven.
- **No CLI command, no orchestration across multiple venue sessions.** One `VenuePipeline`
  instance is one venue session.

## Validation

**Synthetic only.** Every behaviour in this milestone is established by unit tests over
hand-built `TrackObservation` sequences at successive venue instants, using the same
gating/decision/identity configuration builders (`association_builders.py`,
`identity_builders.py`) already established by V0.4.2 and V0.4.3. This proves the wiring
contract; it says nothing about occlusion, crowding, real multi-camera footage, or a real
venue — the same limitation V0.4.2 and V0.4.3 already carry, unresolved by simply calling
them together.

- Human-verified ground truth: **`NOT_ANNOTATED`.** No cross-camera identity produced by
  this pipeline has been checked against a human annotation.
- Proxy/system metrics: **none emitted.** No duplicate-count figure, no merge rate, no
  false-merge rate is produced by this milestone; it is a runtime seam, not a reporting
  layer.

## Known limitations

- **No real-world validation whatsoever**, inherited unchanged from V0.4.1–V0.4.3: every
  threshold this pipeline exercises is a development default or an unmeasured design
  choice.
- **No observation adaptation layer exists yet.** A caller must already have a projector,
  calibration, and venue-time alignment in place to construct the `TrackObservation`s this
  pipeline consumes; V0.4.4 does not lower that bar.
- **`expire()` is entirely caller-driven.** A caller that processes many instants without
  ever calling `expire` will accumulate active and retired venue subjects up to
  `VenueIdentityConfig.max_venue_subjects`, at which point `registry.create()` starts
  refusing — the same caller-driven-expiry limitation V0.4.3a already documents, now also
  reachable through `VenuePipeline.expire`.
- **No duplicate-occupancy suppression, no venue-level headcount.** A `VenueInstantResult`
  reports `active_subjects`; nothing consumes that count into a product metric.
- **Case-4 cross-subject conflict (V0.4.3b) remains unresolved.** `VenuePipeline` surfaces
  the `REFUSED` outcome unchanged; it adds no reconciliation policy of its own.
- **No multi-session or multi-venue orchestration.** One `VenuePipeline` instance is one
  venue session; running several concurrently, or handing one off between processes, is
  outside this milestone's scope.

## Next architectural seam

The next seam is consuming `VenuePipeline`'s per-instant output into venue-level evidence
and decision support: aggregating `VenueInstantResult`s over a session into duplicate-aware
occupancy and reporting (a versioned JSONL contract, `schema_version`-stamped, following the
existing `reporting.py` convention), and — as a distinct, separately-approved piece of
work — a confidence-aware policy for the case-4 cross-subject conflict V0.4.3b deliberately
leaves unresolved. Neither is built here.
