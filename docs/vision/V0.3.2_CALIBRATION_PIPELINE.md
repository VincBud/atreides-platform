# V0.3.2 — Calibration Pipeline Exposure & Validation Tooling

**Status:** implemented · **Substep:** V0.3.2 of V0.3 · **Not production ready**

## Purpose

V0.3.0 built the behaviour signal architecture and V0.3.1 built ground-plane
calibration, but neither was reachable from the actual runtime. Both were
proven only by tests.

V0.3.2 makes them usable and inspectable:

- behaviour analysis is exposed through the CLI, explicitly opt-in;
- signals leave the process as a **versioned, machine-readable JSONL contract**
  a future intelligence layer can consume without parsing logs;
- calibration can be **validated numerically** and **inspected visually**.

No new behaviour intelligence was added. There is still no classification, no
risk score, and no interpretation of any signal.

## Runtime architecture

```text
video
  → RF-DETR              (unchanged)
  → OC-SORT              (unchanged)
  → camera-local track
  → MotionProjector      ← NormalizedFrameProjector or GroundPlaneProjector
  → BehaviorAnalyzer     → BehaviorFrame (snapshots: position + signals)
  → JsonlBehaviorWriter  → versioned JSONL
```

New and changed modules:

| Module | Role |
|---|---|
| `behavior/reporting.py` | **New.** Schema version, record building, streaming writer |
| `behavior/models.py` | `BehaviorSubjectSnapshot` added; `BehaviorFrame.from_snapshots` |
| `calibration/projector.py` | `project_from_venue` — narrow inverse for drawing |
| `visualization/calibration_overlay.py` | **New.** Renders a calibration onto a frame |
| `video/source.py` | `read_reference_frame` — one still from an image or video |
| `config.py` | `resolve_camera_id` — precedence and conflict rules |
| `cli.py` | Flags, projector selection, `calibration` subcommands |
| `video/processor.py` | Optional `behavior_writer` collaborator |

The behaviour layer still does not import the calibration package. Calibration
provenance is flattened into plain data by the composition root, which is what
keeps behaviour analysis usable with no calibration at all.

## CLI

Behaviour analysis is **opt-in and off by default**. A command without the new
flags behaves exactly as before — same video, same overlays, same files.

```bash
# Normalized (camera-local) behaviour signals
atreides-vision run \
  --input data/input/clip.mp4 \
  --output artifacts/tracked.mp4 \
  --behavior-output artifacts/behavior.jsonl \
  --camera-id cam_01

# Calibrated venue metres
atreides-vision run \
  --input data/input/clip.mp4 \
  --output artifacts/tracked.mp4 \
  --behavior-output artifacts/behavior.jsonl \
  --calibration config/calibration.json
```

| Flag | Default | Meaning |
|---|---|---|
| `--behavior-output` | off | Write behaviour JSONL. **This is what enables behaviour analysis.** |
| `--calibration` | off | Ground-plane calibration. Switches units to metres. Requires `--behavior-output` |
| `--camera-id` | from calibration/zones | Camera namespace for behaviour records |

`--calibration` without `--behavior-output` is rejected rather than silently
having no effect.

### Calibration inspection

```bash
atreides-vision calibration validate --calibration config/calibration.json

atreides-vision calibration render \
  --calibration config/calibration.json \
  --input data/input/clip.mp4 \
  --output artifacts/calibration.png \
  --grid-spacing 1.0
```

## Behaviour output contract

**Schema version: `0.3.2`.** JSONL, one object per line. First line is a
`run_metadata` record; every line after it is an `observation`.

### `run_metadata`

```json
{
  "record_type": "run_metadata",
  "schema_version": "0.3.2",
  "camera_id": "cam_01",
  "space": "ground_plane_metres",
  "position_unit": "m",
  "is_physical": true,
  "identity_scope": "camera_local_track",
  "source": {"path": "clip.mp4", "width": 1920, "height": 1080, "fps": 25.0},
  "calibration": {
    "venue_id": "example_venue",
    "surface_id": "ground",
    "reference_frame": {"width": 1920, "height": 1080},
    "correspondence_count": 6,
    "reprojection": {
      "mean_venue_error_m": 0.000243,
      "max_venue_error_m": 0.000597,
      "mean_image_error_px": 0.015,
      "max_image_error_px": 0.026,
      "relative_error": 2.2e-05,
      "venue_extent_m": 10.8167,
      "measures": "fit self-consistency, not validated real-world accuracy"
    }
  }
}
```

`"calibration": null` in normalized mode.

### `observation`

One per subject per frame:

```json
{
  "record_type": "observation",
  "schema_version": "0.3.2",
  "camera_id": "cam_01",
  "frame_index": 123,
  "timestamp_seconds": 4.92,
  "subject": {"track_id": 17},
  "position": {"x": 4.21, "y": 8.73, "space": "ground_plane_metres", "unit": "m"},
  "signals": [
    {"type": "speed", "value": 1.24, "unit": "m/s", "quality": 1.0},
    {"type": "acceleration", "value": -0.08, "unit": "m/s^2", "quality": 1.0}
  ],
  "venue_id": "example_venue",
  "surface_id": "ground"
}
```

### Design decisions

**Subject identity** is `camera_id` (top level) plus `subject.track_id`. There
is no venue-person id, no persistent identifier, and nothing biometric.

**Position and signals are separate.** `position` is an observation — where the
anchor projected to on *this* frame. `signals` are derived over a window. A
record may carry a position and an empty `signals` list, which means "seen here,
not yet enough history to measure motion". That is **not** the same as a zero
speed, and the format keeps them distinguishable.

**Units travel with values.** Every position carries its `space` and `unit`;
every signal carries its `unit`. A consumer never has to guess whether a number
is metric.

| Space | `position.unit` | speed | acceleration | heading | stationary |
|---|---|---|---|---|---|
| `normalized_image` | `normalized_frame_unit` | `normalized_frame_unit/s` | `normalized_frame_unit/s^2` | `rad/s` | `s` |
| `ground_plane_metres` | `m` | `m/s` | `m/s^2` | `rad/s` | `s` |

**Redundancy is deliberate.** `schema_version`, `camera_id` and (in metric mode)
`venue_id`/`surface_id` repeat on every line. JSONL is consumed a line at a
time, and lines from several cameras may later be merged into one stream — a
line that cannot be interpreted alone would eventually be misinterpreted.

**Ordering is deterministic**: frames in processing order, subjects in tracker
order, signals in a fixed type order. Identical input produces a byte-identical
file.

**Provenance** identifies the calibration without repeating it. The full
correspondences stay in the calibration file; the record carries what is needed
to identify and judge the fit.

## Camera ID resolution

Behaviour records are namespaced by camera, so the id is half of every subject
reference. Precedence, highest first:

1. `--camera-id`
2. `calibration.camera_id`
3. `zones.camera_id`

**Disagreement is always an error, never a silent win for the higher source.**
If a calibration says `cam_01` and the operator passes `cam_02`, one of them is
wrong about which camera produced the footage, and guessing would attach one
camera's floor geometry to another camera's name.

**No default is invented.** With behaviour enabled and no source supplying an
id, the run fails with a message naming all three options. A placeholder would
silently merge records from different cameras.

## Projector selection

| Condition | Projector | Thresholds |
|---|---|---|
| `--behavior-output`, no `--calibration` | `NormalizedFrameProjector` | `BehaviorAnalysisConfig()` (normalized) |
| `--behavior-output` + `--calibration` | `GroundPlaneProjector` | `for_ground_plane_metres()` |

The projector and its thresholds always travel together, enforced by
`intended_space` on the config: the analyzer refuses a mismatched pairing.
Mixing them is silent and severe — normalized thresholds under a metric
projector mean nobody is ever stationary.

**An invalid calibration is a hard failure.** There is no fallback to
normalized coordinates, because that would keep the output looking valid while
silently changing every value's physical meaning. Calibration is loaded *and
solved* before the video is opened, so a broken one stops the run at startup.

## Calibration validation command

`atreides-vision calibration validate` reports:

```text
Calibration: config/calibration.example.json
Camera:      cam_01
Venue:       example_venue
Surface:     ground
Reference:   1920x1080
Points:      6
Homography:  solved
Reprojection error
  venue:     mean 0.0002 m, max 0.0006 m
  image:     mean 0.01 px, max 0.03 px
  relative:  0.0000 (0.00% of the 10.82 m calibrated region)
```

It prints **no semantic verdict** — no GOOD/BAD/SAFE/PRODUCTION-READY — because
no validated threshold exists to compare against. It states explicitly that
reprojection error measures fit self-consistency, and warns when a calibration
has exactly four points that a near-zero error says nothing about whether the
points were measured correctly.

## Visual calibration diagnostics

`atreides-vision calibration render` draws onto a still:

- the **venue grid** at configurable metre spacing, anchored on whole metres
- the **calibrated region hull**, so extrapolation beyond it is visible
- the **venue origin and +x / +y axes**
- each **reference point**, with its index and venue coordinates

Reference points are drawn at their *stated image position*, not by projecting
their venue coordinates back — so a point measured against the wrong spot shows
up as a marker in the wrong place, which is exactly the failure this view
exists to catch and the one reprojection error cannot.

Inspection only: no click handling, no GUI, no editing, no automatic point
detection.

**This is the check that matters.** Do the grid lines follow the real floor?

## Inverse projection

`GroundPlaneProjector.project_from_venue` inverts the *effective* transform, so
overlays land correctly on rescaled frames. Deliberately narrow: it exists for
diagnostics and drawing, no raw matrix is exposed, and behaviour algorithms
never see it — measurement runs image-to-venue only. Non-invertible transforms
raise `CalibrationError`; venue points with no image position raise
`ProjectionError`. Forward↔inverse round trips are tested at several
resolutions.

## Frame resolution

The V0.3.1 contract holds through the whole pipeline: a calibration authored at
1920×1080 produces the same venue coordinates when the video is decoded at
960×540, verified end-to-end through the JSONL. Aspect-ratio changes still warn
— a cropped or stretched frame is not a rescaled one, and no rescale can undo
that.

## Multi-camera output boundary

Two calibrated cameras sharing a venue frame produce records that stay
**strictly separate**, even when everything else coincides. The test drives two
cameras whose tracker assigns **the same numeric track id**, observing the same
physical trajectory, producing the same venue coordinates at the same
timestamps — and asserts:

- both recover the same venue positions (to 1e-5 m) and same speed;
- records differ only by `camera_id`;
- merging both files keeps every record uniquely keyed;
- no field anywhere asserts shared identity.

**Spatial agreement is not identity evidence.** Two cameras placing someone at
`(12.4, 7.1)` and `(12.5, 7.0)` are two independent observations. Proximity may
*later* become one input to an association layer; V0.3.2 draws no conclusion
from it.

## Privacy boundary

Unchanged from V0.3.0/V0.3.1 and asserted on the serialised output: no facial
recognition, no appearance embeddings, no biometric identifiers, no ReID, no
persistent identity, no cross-camera association, no venue-person ids, no
demographic attributes, no semantic behaviour labels, and no risk scores.

Two different things are asserted there. Facial recognition, biometric
identifiers, persistent identity and demographic attributes are permanent
product boundaries. Cross-camera association and venue-person ids are simply
absent from V0.3.2 — they are V1 product capabilities, and the venue-local
identity they will produce is temporary and session-scoped, not persistent
identity.

A camera-local track remains temporary technical state, discarded when the
process exits.

## Synthetic validation

End-to-end, through the real `VideoProcessor` with fake detector and tracker
(no model weights, no network):

| Quantity | Expected | Produced |
|---|---|---|
| Venue position | analytic path | matches to < 1e-5 m |
| Speed | 1.4 m/s walked | 1.4 m/s (rel. 1e-4) |
| Timestamp at frame 51 @ 25 FPS | 2.0 s | 2.0 s |
| Half-resolution decode | same metres | matches to < 1e-6 m |
| Two cameras, same walk | same speed | agree to rel. 1e-4 |

Rendering is unaffected: a run with behaviour enabled produces **byte-identical
frames** to one without.

## Real-world validation boundary

**No metric claim is made about real footage.** We have no trustworthy measured
venue geometry for the V0.2.1 validation clips, so V0.3.2 does not claim any
real-world accuracy, validated walking speed, or person-to-person distance in
metres. Every metric number in this document comes from synthetic geometry with
a known analytic answer.

`config/calibration.example.json` remains labelled SYNTHETIC / EXAMPLE ONLY,
and a test asserts that label is present.

## Fixed-camera assumption

**Ground-plane calibration assumes the camera geometry never changes.** Metric
output silently becomes wrong after:

- physical movement or knocks
- pan, tilt or rotation
- zoom or lens change
- digital cropping or re-framing
- image-stabilisation geometry changes
- any other geometric alteration

Nothing detects this. There is no camera-movement monitoring, and V0.3.2
deliberately does not guess at one with heuristics. Treat a calibration as
valid only for footage from the camera in the exact pose it was measured in.

## Performance

Measured with fake detector and tracker on deterministic synthetic input —
**detector inference is excluded**, so this measures the behaviour and output
layers only.

600 frames, 8 tracked people per frame, 1920×1080, 9 interleaved repetitions,
median:

| Mode | Total | Per frame | Overhead |
|---|---|---|---|
| Behaviour off | 0.620 s | 1.034 ms | — |
| Normalized | 0.782 s | 1.303 ms | **+0.270 ms/frame** |
| Ground plane | 0.771 s | 1.285 ms | **+0.251 ms/frame** |

≈0.03 ms per person-observation; JSONL ≈472 bytes per record. Metric and
normalized are indistinguishable within noise — projection is a handful of
multiplications either way, and serialisation dominates.

**This says nothing about real-time capability.** It excludes the detector,
which dominates end-to-end cost by orders of magnitude (single-digit FPS on
CPU), and it uses synthetic frames.

## Known limitations

1. **No real-venue metric validation.** All accuracy evidence is synthetic.
2. **Planar ground only.** Stairs, balconies, platforms and multiple floors are
   silently mismeasured.
3. **Fixed-camera assumption with no monitoring** (see above).
4. **A track ID is not a person.** Occlusion still splits one person into
   several ids, so per-subject records are per-*tracklet*.
5. **Reprojection error is self-consistency, not accuracy**, and four-point
   calibrations always report zero.
6. **Zone context is not wired.** The output format carries an optional
   `zone_ids` field and the analyzer accepts one, but the processor does not
   populate it — the zone layer works in normalized image space and exposing
   per-track membership cleanly is deferred rather than forced.
7. **No behaviour visualisation.** Signals are data only; nothing is drawn.
8. **Metric behaviour thresholds are unvalidated development defaults.**
9. **JSONL is uncompressed and unsampled** — one record per subject per frame.
   A busy scene produces large files; no sampling control exists yet.
10. **No lens-distortion model.** Wide-angle and fisheye cameras violate the
    pinhole assumption a homography rests on.
11. **Behaviour analysis is single-camera per run.** Multi-camera means several
    runs producing several files.

## Verification

1145 tests pass (1008 before this milestone, 137 added), `ruff check`,
`ruff format --check` and strict `mypy` all clean.

### One latent bug found and fixed

`visualization/overlay.py` imported `TrajectoryStore` at runtime, which pulls in
the `video` package, whose `__init__` imports the processor, which imports
`overlay` — a cycle that only failed when `visualization` happened to be
imported first. It never triggered before because the CLI always imported the
processor first. The new `calibration_overlay` module imports `visualization`
first and exposed it.

The fix is minimal: the import is type-only (`TYPE_CHECKING`), which it always
could have been since the module uses `from __future__ import annotations`. No
runtime behaviour changed. Two regression tests import the packages in each
order in a subprocess.

## Next milestone — V0.3.3

Recommended bounded scope:

1. **Real-venue calibration measurement and validation.** Measure reference
   points on an actual floor with a tape measure or laser, then quantify
   accuracy against known distances not used in the fit. This is the single
   thing blocking every metric claim.
2. **Zone context wiring.** Expose per-track zone membership from
   `ZoneAnalyzer` and pass it through, so records carry where they happened.
3. **Output volume control.** Sampling interval and/or compression for the
   behaviour stream.
4. **Camera-movement / calibration-integrity monitoring**, so a nudged camera is
   flagged rather than silently producing wrong metres.

Still out of scope for this milestone: ReID, cross-camera association,
venue-person identity, interaction signals, group detection, crowd-risk
interpretation, aggression or intoxication or distress classification, risk
scoring, decision engines, operator alerting, LLM integration, model training,
automatic calibration, camera pose recovery, SLAM, 3D reconstruction, depth
estimation, full venue configuration redesign and any calibration GUI.
