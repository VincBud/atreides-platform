# V0.4.5 — Fusion Observability & Reporting

**Status:** implemented · **Engineering milestone:** V0.4.5 ·
**Product generation:** V1 · **Not production ready**

## Purpose

V0.4.4 wired `AssociationEngine` and `VenueSubjectRegistry` together into `VenuePipeline`,
a runtime seam that works — but produces nothing a process outside that object graph can
inspect. Answering "what did association decide?", "what did fusion do with it?", or "what
does this venue subject's provenance look like right now?" required reading Python objects
directly.

V0.4.5 makes that runtime inspectable, and nothing more: a deterministic, explainable,
schema-versioned JSON Lines record of exactly what `VenueInstantResult` and
`VenueSubjectRegistry` already know, per venue instant. It answers:

- what observations were considered at this venue instant;
- which cross-camera pairs were comparable, and what `AssociationOutcome` each produced;
- what evidence, support and confidence justified each association decision;
- which decisions fusion applied, no-opped, refused, or ignored, and why;
- which `VenueSubjectId`s currently exist, and which camera-local tracklets belong to each;
- why a potential merge was not performed (a `REFUSED` `IntegrationOutcome` names both
  conflicting subjects; an `IGNORED` one names the non-positive `AssociationOutcome` behind
  it);
- what changed in venue-local identity state at this instant.

**This is observability only.** It recomputes nothing: no `AssociationOutcome`, no
`IntegrationOutcome`, no membership decision is decided here — every field is read from
already-produced `VenueInstantResult` and `VenueSubjectRegistry` state, reusing each
domain's own `to_record()` wherever one already exists
(`AssociationRound.to_record()`, `VenueSubject.to_record()`). No reporting output feeds back
into association or fusion; nothing in this module is a permitted input anywhere upstream.

## Architectural position

```text
detection → camera-local tracking → calibration / spatial context
  → venue-time alignment / fan-in            (V0.4.0)
  → comparability gating + geometry          (V0.4.1)
  → deterministic association                (V0.4.2)
  → temporary venue-local identity           (V0.4.3a — identity/)
  → association → identity integration       (V0.4.3b — fusion/)
  → per-venue-instant runtime wiring         (V0.4.4 — venue_pipeline.py)
  → deterministic observability/reporting    ← V0.4.5 builds this (venue_pipeline_reporting.py)
  → venue-level evidence → decision support  (later)
```

```text
services/vision/src/atreides_vision/
├── venue_pipeline.py             # V0.4.4 — VenuePipeline, VenueInstantResult
└── venue_pipeline_reporting.py   # V0.4.5 — instant_record, JsonlVenuePipelineReportWriter
```

`venue_pipeline_reporting.py` is a single top-level module, placed alongside
`venue_pipeline.py` for the same reason that module itself is top-level: it needs to read
`association`, `fusion`, `identity` and `venue_pipeline` output together, and no package's
own boundary guard permits that reach from inside it. It adds `jsonl` (the shared
line-oriented writer every other output stream in this repository already uses) to
`venue_pipeline`'s own reach, and nothing further. Enforced by
`test_venue_pipeline_reporting_boundaries.py`, an AST-walked import guard following the same
pattern as `test_venue_pipeline_boundaries.py`.

It does **not** modify `venue_pipeline.py`. `VenuePipeline.process_instant` and `expire` are
untouched — this milestone is an additive consumer of their existing, already-complete
`VenueInstantResult`, called by the caller *after* `process_instant` returns, never from
inside it.

## Public surface

```python
VENUE_PIPELINE_REPORT_SCHEMA_VERSION = "0.4.5"

@dataclass(frozen=True, slots=True)
class VenuePipelineReportMetadata:
    session_id: str

    def to_record(self) -> dict[str, Any]: ...


def instant_record(
    result: VenueInstantResult, registry: VenueSubjectRegistry, session_id: str
) -> dict[str, Any]: ...


class JsonlVenuePipelineReportWriter:
    def __init__(
        self,
        path: Path | str,
        metadata: VenuePipelineReportMetadata,
        compress: bool | None = None,
    ) -> None: ...

    @property
    def path(self) -> Path: ...
    @property
    def metadata(self) -> VenuePipelineReportMetadata: ...
    @property
    def instants_written(self) -> int: ...
    @property
    def is_compressed(self) -> bool: ...

    def write_instant(self, result: VenueInstantResult, registry: VenueSubjectRegistry) -> None: ...
    def release(self) -> None: ...
    def __enter__(self) -> Self: ...
    def __exit__(self, ...) -> None: ...
```

That is the entire surface this milestone adds. `instant_record` is the pure, stateless
builder function; `JsonlVenuePipelineReportWriter` is the thin, stateful wrapper around it
and `JsonlStreamWriter` for callers that want a file on disk. Both are usable independently
— a caller doing its own aggregation can call `instant_record` directly and never touch the
writer.

## Record schema

One JSON object per line. The first line is a header (`record_type: "venue_pipeline_report"`,
written on writer construction, raising immediately on an unwritable destination). Every
subsequent line is one `record_type: "venue_instant"` record, one per call to
`write_instant`:

```json
{"record_type":"venue_pipeline_report","schema_version":"0.4.5","session_id":"...","identity_scope":"venue_local_temporary","association_scope":"cross_camera_pairwise"}
{"record_type":"venue_instant","schema_version":"0.4.5","session_id":"...","venue_seconds":10.375,"association":{...},"integration":{...},"active_subjects":[...]}
```

Every record repeats `schema_version` and `session_id`, matching every other stream in this
repository: JSONL is read one line at a time, and a line that cannot be interpreted alone
will eventually be misinterpreted.

A `venue_instant` record's three bodies:

- **`association`** — `AssociationRound.to_record()`, unchanged: every observation
  considered, every candidate pair's outcome (`associated`, `ambiguous`, `unassociated`,
  `not_comparable`), with its reasons, support and confidence, and an `outcome_counts` entry
  for all four `AssociationOutcome` values.
- **`integration`** — the round's `venue_seconds`, plus one entry per decision, each
  carrying: the `IntegrationOutcome` fusion produced (`applied`, `no_op`, `refused`,
  `ignored`), fusion's own `detail` string, the candidate pair as two
  `{camera_id, stream_epoch, track_id}` tracklet keys, and the `venue_subject_id`(s) the
  outcome concerns — empty for `ignored`, one for `applied`/`no_op`, two (never merged) for a
  `refused` cross-subject conflict.
- **`active_subjects`** — every venue subject active immediately after this instant's
  integration, each as a full `VenueSubject.to_record()`: `venue_subject_id`,
  `created_at_seconds`, `last_activity_seconds`, `retired_at_seconds`, and `members` (the
  active camera-local tracklets, each with `camera_id`, `track_id`, `stream_epoch`,
  `joined_at_seconds`).

`MembershipOutcome` and `IntegrationResult` (`fusion/models.py`) have no `to_record()` of
their own — V0.4.3b never needed one. Rather than add reporting responsibility to
`fusion/models.py`, the two small helpers that serialise a `MembershipOutcome`
(`_tracklet_key_record`, `_membership_outcome_record`) live in this module, beside the
runtime path rather than inside it.

## Provenance chain

A `venue_subject_id` appearing in `active_subjects` always resolves back to the
`(camera_id, stream_epoch, track_id)` observations that produced it, through that same
subject's `members` list — nothing is summarised away. A `venue_subject_id` appearing in an
`integration` outcome's `subject_ids` names the same identity `active_subjects` describes;
the two are never a different type or a different namespace for the same thing. Pinned by
`TestProvenanceSurvivesFusion`.

## Determinism

Same input, same output, byte-for-byte. `instant_record` performs no iteration over an
unordered collection of its own: `AssociationRound.to_record()`, `IntegrationResult.outcomes`
and `VenueSubjectRegistry.active_subjects()` are already canonically ordered by their own
layer (candidate key, decision order, subject sequence respectively), and this module adds
no further sort or set. Pinned by `TestDeterminism`, which checks two independent pipeline
runs of the same input produce an identical record, and that permuting observation
enumeration order within an instant changes nothing about the resulting record.

## Single-camera behavior

A single-camera session produces the same record shape as any other: every candidate pair
is same-camera, every `AssociationOutcome` is `not_comparable`, every `IntegrationOutcome` is
`ignored`, `active_subjects` stays empty — a fully-formed, legal record, not a special case.
Pinned by `TestSingleCameraDegeneratePath`.

## Zero-observation behavior

An empty `VenueInstantResult` (no observations processed this instant) produces a legal,
minimal `venue_instant` record: `association.decisions == []`, `integration.outcomes == []`,
`active_subjects` reflecting whatever the registry already held. Pinned by
`TestZeroObservationInstant`.

## Failure and refusal semantics

`instant_record` raises nothing of its own beyond what the domain types it reads already
raise (none, in the ordinary case — every field it touches is already-validated, frozen
state). `JsonlVenuePipelineReportWriter` raises `FusionError` — already the integration
layer's own reporting-contract exception (see its docstring in `errors.py`) — for every
failure mode it introduces: an unwritable destination (raised immediately at construction,
before any instant is written), a write after `release()`, or a serialisation failure. A
writer failure never raises `AssociationError` or `IdentityError`, and never mutates
`VenuePipeline`, `AssociationEngine` or `VenueSubjectRegistry` state — a caller can construct
a pipeline, have report-writer construction fail, and continue processing instants on that
same pipeline unaffected. Pinned by `TestWriterIntegration`.

All four `AssociationOutcome` values and all four `IntegrationOutcome` values are
independently exercised and asserted distinguishable in the record: `TestAssociatedOutcomeIsReported`,
`TestUnassociatedOutcomeIsReported`, `TestAmbiguousOutcomeIsReported`,
`TestNotComparableOutcomeIsReported`, and `TestRefusedFusionOutcomeIsReported` (`applied`,
`ignored` and `no_op` are covered incidentally by the same and by
`TestDuplicateCountingIsNotProduced`).

## What V0.4.5 does not do

- **No occupancy, no duplicate-suppression product metric, no cumulative unique-visitor
  count.** `active_subjects`' length is visible in the record; nothing here turns it into a
  headcount metric.
- **No risk or decision-engine output, no decision-support event.**
- **No new association or fusion policy.** Every outcome this milestone reports was already
  decided by V0.4.2/V0.4.3b before this module ever sees it.
- **No embeddings, ReID, appearance evidence, or biometric field of any kind.**
- **No persistent identity store, no cross-session linkage.** `session_id` is a
  caller-supplied label carried through unchanged; this module does not read or write a
  session manifest, and does not import `atreides_vision.venue`.
- **No dashboard or product API shape.** The schema is narrow and single-purpose: one
  instant's association/fusion/identity trail, nothing aggregated across instants, nothing
  formatted for display.
- **No CLI wiring.** No command in `cli.py` was added or changed.
- **No modification of `venue_pipeline.py`.** `VenuePipeline.process_instant` and `expire`
  are byte-for-byte unchanged by this milestone.

## Validation

**Synthetic only.** Every behaviour in this milestone is established by unit tests reusing
the same `VenuePipeline` scenarios `test_venue_pipeline.py` (V0.4.4) already established,
now asserting on the reporting module's own output rather than on `VenueInstantResult`
directly. This proves the reporting contract; it says nothing about occlusion, crowding,
real multi-camera footage, or a real venue — the same limitation every milestone in this
chain already carries.

- Human-verified ground truth: **`NOT_ANNOTATED`.**
- Proxy/system metrics: **none emitted.** This milestone produces no duplicate-count,
  merge-rate or false-merge-rate figure of its own; it reports what association and fusion
  already decided.
- Synthetic correctness — test counts (`pytest --collect-only`, current state):

identical results across two independent runs, identical results across observation
enumeration order, a single-camera session, a zero-observation instant, and a writer failure
that never touches association, fusion or identity state.

## Known limitations

- **No real-world validation whatsoever**, inherited unchanged from V0.4.1–V0.4.4: every
  threshold this record reflects is a development default or an unmeasured design choice.
- **Caller must invoke the writer promptly after `process_instant`.** `VenueSubjectRegistry.get`
  raises `IdentityError` only for a fully purged subject, but a subject reported as
  `active_subjects` by one instant can be retired or purged by a later `expire()` call before
  a caller gets around to reporting it — this module documents, but does not enforce, calling
  `write_instant`/`instant_record` before any further registry-mutating call.
- **No aggregation across instants.** Each record describes exactly one venue instant; a
  reader wanting a session-level occupancy or duplicate-suppression view must aggregate
  these records itself — this milestone deliberately does not do that aggregation.
- **No consumer wired in `cli.py`.** No command in this repository currently produces this
  stream from a real run; it is available to be called from a future orchestration point.
- **Case-4 cross-subject conflict (V0.4.3b) remains unresolved.** This milestone reports the
  `REFUSED` outcome and both conflicting subject ids; it adds no reconciliation policy of its
  own.

## Next architectural seam
