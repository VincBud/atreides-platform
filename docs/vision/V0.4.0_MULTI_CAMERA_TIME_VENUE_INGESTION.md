# V0.4.0 — Multi-Camera Time & Venue Ingestion Foundation

**Status:** implemented · **Engineering milestone:** V0.4.0 · **Product generation:** V1 ·
**Not production ready**

## Purpose

Every milestone up to V0.3.6 processed **one video per run**. Camera identity existed as a
string stamped onto output, but nothing in the system could hold two cameras at once, and
"seconds" needed no qualification because there was only ever one clock.

V0.4.0 builds the foundation underneath multi-camera operation: a way to describe N camera
streams as one venue session, place every decoded frame on one **session-relative venue
timeline** with its **uncertainty stated**, distinguish a camera's recordings from each
other across a restart, and hand a later layer a **deterministically ordered**, fully
**provenanced** stream of observations.

**It coordinates time and provenance. It does not compare people.** There is no
association, no venue-local identity, no cross-camera matching and no appearance
information anywhere in this layer. Those are V1 capabilities that remain unbuilt; see
[What V0.4.0 does not do](#what-v040-does-not-do).

## Why this had to come first

Association is the capability that turns several cameras into one venue view. It is also
the capability where a mistake is most expensive: per `CLAUDE.md`, a wrong merge corrupts
every venue-level number above it and is harder to detect than a missed one.

Association compares observations across cameras, which means it compares them **in time**.
An association layer built on a fabricated common clock would be unfalsifiable — it would
produce merges that look reasonable and are wrong for a reason nothing in the data records.
Two properties of the pre-V0.4.0 code made exactly that fabrication easy:

- `VideoProcessor` derived its own timestamps internally (`(frame_index - 1) / source_fps`),
  so time was owned by the camera-local loop rather than above it.
- `FileVideoSource` silently substituted a 25.0 FPS fallback when a container reported a
  bogus frame rate, and **nothing downstream could tell**. Single-camera, that scales every
  timestamp by one wrong constant and signals stay internally consistent. Multi-camera, a
  stream read as 25 FPS that is really 15 drifts against a correct stream **linearly** —
  four minutes of error after ten minutes of footage, with the data saying nothing.

So V0.4.0's real deliverable is not a scheduler. It is a time domain honest enough that
association can later be **validated** on it.

## Architecture

```text
camera-local processing
  → venue-time alignment / multi-camera fan-in     ← V0.4.0 builds this
  → future association
  → future temporary venue-local identity
  → future venue-level evidence
  → future Risk / Decision Support
```

```text
services/vision/src/atreides_vision/
├── timing.py            # FrameRateSource, TimeAlignmentBasis, TimeUncertainty,
│                        # StreamRef, StreamFrame — shared by video/ and venue/
└── venue/
    ├── models.py        # StreamActivity, StreamAbsence, VenueTick
    ├── manifest.py      # VenueSessionManifest and its loader (schema 0.4.0)
    ├── timebase.py      # VenueTimebase — source time → venue time, with uncertainty
    ├── scheduler.py     # StreamCursor protocol, merge_streams — the ordering rule
    ├── session.py       # VenueSession facade, VideoSourceCursor
    └── reporting.py     # session record stream (schema 0.4.0)
```

`timing.py` is top-level rather than inside `venue/` on purpose: `video/` must consume
`StreamFrame` and `FrameRateSource`, and if those lived in `venue/` then `video/` would
import `venue/` — a layering inversion. The dependency runs one way only:
`venue/ → video/ → timing.py`.

Three boundaries are load-bearing:

**Venue time is owned above camera-local processing.** `VideoProcessor` no longer derives
timestamps; it receives a `StreamFrame` that has already been placed on the venue timeline.
No detector, tracker or analyzer knows a venue exists.

**`venue/` cannot see people.** It imports only `video/`, `timing`, `errors` and `jsonl` —
never `behavior`, `interaction`, `crowd`, `zones`, `calibration`, `tracking` or `detection`.
This is asserted by a test that walks the import AST over every module in the package
(recursively, including any future subpackage), not left to reviewer discipline. A venue
layer that could reach a track is a venue layer that could quietly start matching them.

One residual is documented rather than papered over: an AST walk sees `import` statements,
so a dynamic `importlib.import_module(...)` would evade it. Nothing in the package does
that, and the guard is a tripwire against drift, not a sandbox.

**`SubjectRef` is untouched.** It remains exactly `(camera_id, track_id)`. Stream lifecycle
lives *above* camera-local identity, never inside it.

## Venue time

Every frame carries **two** times, answering different questions:

| | Meaning | Restarts? |
| --- | --- | --- |
| `source_seconds` | elapsed time inside that stream, `(frame_index - 1) / fps` | yes — at every epoch boundary |
| `venue_seconds` | the same instant on the one session timeline, `source_seconds + offset` | no — monotonic across the session |

**Venue time is session-relative.** Zero is the start of the session, not a wall-clock
instant. No date, no time of day, no NTP dependency, and no absolute timestamp is
synthesised from a file's mtime or container metadata — a recorded CCTV file carries no
trustworthy absolute capture time, and inventing one is the same class of error this
project rejects everywhere else.

Camera-local analyzers receive **venue seconds**, because source seconds move backwards at
a restart and `IntervalSampler` and every history store would misread that.

Absolute time is a *deployment* fact. Should a deployment ever have one, it enters as a
single optional session-level field and `utc = session_start + venue_seconds` becomes a
reporting concern. No runtime type changes. That field is deliberately **not** added now.

### Single camera is bit-identical

With one camera and no declared offset, `venue_seconds == source_seconds ==
(frame_index - 1) / fps` — exactly, not approximately. The offset is added in float and
`x + 0.0 == x` in IEEE 754, so V0.3.x numbers do not move in any digit. This is pinned by a
test asserting `==` rather than `approx`, across five frame rates, and by a test comparing a
venue-driven run against `VideoProcessor.run()` frame array by frame array.

**One camera is not a different code path.** A one-camera venue session is a session with
one stream. There is no `if multi_camera:` branch anywhere.

## Timing uncertainty

```python
TimeUncertainty(basis, half_width_seconds)
```

`half_width_seconds` is a symmetric bound — the true instant is believed to lie within
`± half_width` of the stated venue time. It is not a standard deviation and not a
probability.

The rules that keep it honest:

- **`NOT_ESTABLISHED` is the default, not a fallback.** A stream whose offset nobody
  declared has `half_width_seconds is None`. `None` is not `0.0`; it does not compare and
  does not do arithmetic.
- **The two fields are validated as one.** `NOT_ESTABLISHED` **iff** `None`. "Aligned,
  accuracy unknown" is not a representable state — it is `NOT_ESTABLISHED`.
- **Zero is rejected at construction.** So are negatives, NaN and infinity. A declared zero
  would claim two streams are aligned exactly, which no manually declared offset ever is.
- **Declaring an offset without an accuracy is a manifest error, not a default.** The
  loader will not type a number the operator did not.
- **An `ASSUMED` frame rate forecloses declared *accuracy*, but not placement.** A stream
  whose frame rate had to be guessed may still carry a declared `start_offset_seconds` —
  that offset positions it on the venue timeline. Its `TimeUncertainty` is nevertheless
  forced to `NOT_ESTABLISHED` whatever accuracy the operator supplied, because a fixed
  half-width cannot describe an error that grows linearly with elapsed time. A discarded
  accuracy is logged, never dropped silently.

  Placement and accuracy are deliberately separate concerns. Coupling them, as an earlier
  revision did, made an ordinary NVR export — a camera that restarted mid-session, from a
  container reporting a useless frame rate — unrepresentable, and left the operator's only
  escape route being to invent a `declared_fps`. That would have converted a guess into a
  typed trustworthy fact: precisely the laundering this milestone exists to prevent.
- **Unknown absorbs.** A tick's `alignment` is `NOT_ESTABLISHED` if *any* contributor is;
  otherwise it is the widest contributing half-width.
- **There is no threshold, no comparison operator and no `is_aligned_enough()`.** A boolean
  derived from a half-width is the first step toward deciding two observations are the same
  person. Consumers carry uncertainty forward and report it; they never collapse it.

### Frame-rate provenance

`FrameRateSource` records where a frame rate came from, because every source-relative
timestamp is derived from it:

| | Meaning |
| --- | --- |
| `CONTAINER` | read from the container and usable as reported |
| `ASSUMED` | the container reported nothing usable and a fallback was applied — a guess |
| `DECLARED` | supplied by the operator in the manifest, overriding the container |

`ASSUMED` is the state that used to be invisible. It is now a typed fact carried on
`VideoMetadata` and recorded in the session provenance, and it constrains what alignment a
stream may claim.

## Stream epoch

A camera identifier alone cannot distinguish `camera_01` before a reconnect from
`camera_01` after one. `StreamRef(camera_id, stream_epoch)` can.

`stream_epoch` is the **0-based index of the source in that camera's ordered source list in
the manifest**. Not a clock, not a UUID, not a content hash, not a file mtime — just a
position, so a recorded session's epochs are fully reproducible from the manifest alone.

It is unique within `(session, camera)`, strictly increasing in manifest order,
session-scoped, and **never persisted**.

What it asserts: **crossing an epoch boundary breaks track identity.** `(cam_north, track_7)`
before and after are unrelated tracklets that happen to share an integer. That was already
true and stated in prose; V0.4.0 makes it a type.

`StreamRef.__str__` renders `cam_north#0`, deliberately using `#` where `SubjectRef` uses
`/` (`cam_north/7`). A reader skimming a log must never mistake a stream for a tracklet. A
`StreamRef` never appears inside a `SubjectRef` and never becomes one.

A camera with more than one source **must** declare `start_offset_seconds` on every entry —
the gap between two recordings cannot be guessed, and continuing segment 1 from segment 0's
end time would be a claim about a gap nobody measured.

## N-source fan-in

**Ticks are driven by source events, not by a fixed venue cadence.** Every decoded frame
produces a tick; ticks are emitted in venue-time order.

A fixed venue cadence was rejected because it requires choosing a venue frame rate — a
hardcoded rate in all but name — and then forces a decision about what a camera
"contributes" between its own frames. All three answers are bad: interpolate (fabricates an
observation), hold-last (converts *we did not look* into *we looked and saw this*), or emit
nothing (which is the source-driven design anyway).

A consumer that wants a regular cadence layers the existing `IntervalSampler` on top — the
same mechanism zone metrics, behaviour emission and integrity checks already share. The
cadence choice then sits with the consumer that has a reason for it, rather than being
imposed by ingestion.

Unequal frame rates need no special handling: the merge compares **venue times**, never
frame indices, and never assumes streams tick together.

### Not contributing is a first-class value

Every registered stream that is not in a tick's `contributions` appears in its `absent`
tuple with one of three activities — each a distinct fact a later consumer needs:

| `StreamActivity` | Meaning | Why it must be distinct |
| --- | --- | --- |
| `CONTRIBUTED` | a frame from this stream is in this tick | — |
| `BETWEEN_FRAMES` | the stream covers this instant; its frames fall either side | absence of detection here is **not** evidence of absence of a person |
| `NOT_YET_STARTED` | this instant precedes the stream's first frame | **no coverage** — a different fact from "sampled and saw nobody" |
| `ENDED` | this instant follows the stream's last frame | no coverage; the venue is now partially blind |

No frame is ever synthesised to make timestamps line up. A stream that opens and decodes
zero frames is valid — it is `ENDED` from the first tick and never contributes.

## Determinism

The total order over frames is:

```text
(venue_micros, camera_id, stream_epoch)
```

A fourth key, `frame_index`, is stated in the design for total-order completeness but is
**not** part of the implemented sort and cannot be reached: a stream contributes at most one
frame to any one venue instant, so `(camera_id, stream_epoch)` already discriminates every
pair of contributions within a tick.

`venue_micros = round(venue_seconds * 1_000_000)`. Ordering on an **integer** key means two
streams landing on the same instant compare exactly equal, with **no tolerance constant
anywhere**. A float tolerance was rejected because tolerance-based clustering is not
transitive, which would make the tick a frame lands in depend on input order — precisely
the failure this milestone exists to exclude.

`venue_micros` is the *order*; `venue_seconds` is the *measurement*. Deriving a time from
the key would silently quantise every downstream second, so nothing does.

`camera_id` compares by Python's default `str` ordering (Unicode code point) — never
locale-dependent, never insertion order. `absent` is sorted by `(camera_id, stream_epoch)`.
Each tick carries a 0-based `sequence`, so the order is **recorded in the data** rather than
merely implied by iteration.

**Manifest camera order cannot reach the output.** Cameras supplied A, B, C and C, A, B
produce identical ticks, identical sequence numbers and a byte-identical session record.
This is verified both as a unit test and end-to-end against real decoded MP4s.

## Bounded state

Exactly **one decoded frame is in flight per stream** — `peek()` holds one lookahead frame,
`advance()` consumes it. No tick is retained, no per-stream history is kept, and reporting
is streamed. Memory is O(cameras) and independent of run length. `VenueTick` documents that
it holds decoded frames and must not be retained.

The scheduler never consults `frame_count`, never seeks and never rewinds; it reads until
each cursor is exhausted. (`frame_count` *is* recorded in the session header as provenance —
a container lying about its own frame count is exactly what a diagnostic should surface —
but it never influences the schedule.)

## Scalability

Nothing here hardcodes a camera count, a layout, a quadrant scheme, a coverage area, an
overlap pattern, a mounting geometry, a frame rate or a resolution. Everything iterates the
manifest. **Non-overlapping cameras are the ordinary case** — the scheduler has no notion of
spatial relationship at all, and `venue/` never imports `calibration/`.

## The future-association seam

`VenueSession.ticks()` yields `VenueTick`s. A later association layer attaches **above** the
venue loop as an optional collaborator — the same pattern zones, behaviour, interaction and
crowd already use on `VideoProcessor`.

`VideoProcessor` exposes a three-call pass — `begin(metadata, sink)`, `process(frame, sink)`
per frame, then `finish()`. `run(source, sink)` is a thin wrapper over exactly that sequence
and is unchanged in signature and observable behaviour. `begin()` takes the stream's declared
geometry once, because that is a property of the stream rather than of any one image, and
because the composition root already built this camera's projector from the same
`VideoMetadata`. A processor binds to its first frame's `StreamRef` and **refuses** a frame
from another camera, another epoch, or with non-advancing venue time — one processor follows
one stream, mirroring the guard in the merge below it.

`process()` returns `None`. No per-frame result type was invented, because inventing one now
would pre-build the association contract before anyone has designed it.
When association arrives it changes two things: the loop in `venue/session.py` and that
return type. Neither is a fork.

**What the seam exposes:**

- `StreamRef` — camera identity and stream epoch
- `venue_seconds` and `venue_micros`, per contribution and per tick
- `source_seconds` + `frame_index` — provenance back to the exact frame of the exact file
- `TimeUncertainty`, per stream and per tick
- `StreamActivity` for every camera that did not contribute
- a deterministic total order, with `sequence` recorded in the data

**What it must never expose:**

- venue-local or global person identity of any kind
- appearance descriptors, embeddings, crops, colour histograms, or any pixel-derived
  identity feature
- cross-camera track correspondence, candidate pairs, distance matrices or match scores
- duplicate-count suppression, unique-people counts, or cumulative visitor figures
- persisted per-person state, to disk or across sessions
- camera topology, adjacency, overlap or transition-time models
- any `is_same_person`-shaped predicate
- any boolean or threshold derived from `TimeUncertainty`

Two things in this design sit one inference from association and are named so they can be
watched: a tick carrying several contributions at one instant reads as "simultaneous
observations", and `TimeUncertainty.worst_of` is one step from "aligned enough to merge?".
Neither has an accessor that would let a caller take that step, and `venue/`'s import
boundary is asserted by test.

## Interfaces

### Venue manifest — schema `0.4.0`

```json
{
  "manifest_version": "0.4.0",
  "session_id": "example_session",
  "cameras": [
    {
      "camera_id": "cam_north",
      "sources": [
        {"input_path": "...part1.mp4", "start_offset_seconds": 0.0,
         "offset_accuracy_seconds": 0.5, "declared_fps": 25.0},
        {"input_path": "...part2.mp4", "start_offset_seconds": 612.5,
         "offset_accuracy_seconds": 0.5, "declared_fps": 25.0}
      ]
    },
    {"camera_id": "cam_west", "sources": [{"input_path": "...cam_west.mp4"}]}
  ]
}
```

`camera_id` must be **unique** within a session — deliberately unlike
`ValidationManifest`, which permits duplicates because one physical camera supplies many
independent clips. A venue session asserts the opposite: every stream is one venue at one
time. Two entries with the same id are either one camera with several segments (one entry,
several sources) or an operator error.

The manifest carries identity, sources, offsets and declared frame rates only. It does
**not** carry neighbours, overlaps, adjacency or transition times — that is V3 deployment
metadata and an overlap assumption, and neither belongs here.

See [`config/venue/example.json`](../../config/venue/example.json).

### CLI — `venue inspect`

```bash
uv run atreides-vision venue inspect --manifest config/venue/example.json \
                                     --output artifacts/venue/session.jsonl
```

Deliberately **diagnostic and narrow**. It loads a manifest, opens the sources, walks the
full tick schedule and writes the versioned session record. **It runs no detector and no
tracker**, so it needs no model weights, no network and no GPU, and the whole V0.4.0
deliverable — timing, epochs, fan-in, determinism, provenance — is exercisable in the unit
suite.

Existing commands are untouched: `atreides-vision run ...` behaves exactly as it did, and
the V0.3.6 validation harness is unchanged.

### Session record — schema `0.4.0`

A new, additive JSONL stream: a header carrying `VenueSessionMetadata` (session id, and per
stream its `StreamRef`, path, resolution, fps, `fps_source`, offset and `TimeUncertainty`),
and a closing `VenueSessionSummary` (tick count, frames per stream, first and last venue
instant).

**No frozen V0.3.x schema was changed.** Behaviour stays `0.3.3`, interaction `0.3.4`,
crowd `0.3.5`, validation manifest `0.3.6`.

## What V0.4.0 does not do

Stated plainly, because a foundation is easy to mistake for the capability it supports:

- **No Multi-Camera Association / Fusion.** Nothing compares an observation on one camera
  with an observation on another. This remains an unbuilt **V1** capability — it is not
  deferred to V2.
- **No temporary venue-local identity.** No `VenueSubjectId`, no venue person id, no
  mapping from `SubjectRef` to anything above it.
- **No cross-camera ReID, no appearance embeddings, no face recognition, no biometrics.**
- **No hand-off matching** and no non-overlap transition reasoning.
- **No duplicate-count suppression** and no venue-level headcount. A frame count is not a
  person count.
- **No same-camera fragment stitching.** Crossing an epoch boundary breaks track identity;
  nothing repairs it.
- **No venue-level crowd or interaction fusion.** Behaviour, interaction and crowd remain
  strictly camera-local.
- **No Risk / Decision Engine** and no decision-support alerts.
- **No per-camera signal wiring in a venue session.** `venue inspect` runs no detector or
  tracker; wiring calibration, zones, behaviour, interaction and crowd per camera is a later
  milestone.
- **No live deployment.** No RTSP, no network sources, no reconnect detection, no threads,
  no asyncio. The seam is shaped to accept them; none is built.
- **No absolute wall-clock venue time** and no cumulative unique-visitor figure.
- **No V2 extreme-vision work** and **no V3 hardware work.**
- **No production-readiness claim.**

## Limitations

- **No real-world multi-camera validation.** Determinism, heterogeneous frame rates,
  offsets, restarts and bounded state are proven on synthetic sources and on synthetic
  manifests over real containers. **Synthetic correctness is not real-world robustness.**
  No genuinely simultaneous multi-camera footage exists in this repository — the V0.3.6
  clips are independent captures — so nothing here has met real desynchronised clocks,
  drifting consumer frame rates, or a real reconnect.
- **Alignment is only ever as good as the operator's declaration.** Atreides does not
  measure the offset between two streams and cannot detect a wrong one. A confidently
  declared but incorrect `start_offset_seconds` produces confidently wrong venue times.
  Deriving offsets by cross-correlating stream content would be association by another name
  and is explicitly out of scope.
- **`ASSUMED` frame rates still poison V0.3.x output silently.** `fps_source` is recorded in
  the *new* venue record, but `SourceProvenance.fps` in the frozen behaviour schema `0.3.3`
  and `PerformanceMetrics.source_fps` in validation still cannot express it. A behaviour
  stream read in isolation cannot tell a real 25 FPS from a fabricated one. Surfacing it
  requires bumping a frozen schema — a separate human decision, deliberately not taken here.
- **A tick's co-occurrence is nominal when alignment is `NOT_ESTABLISHED`.** Two frames
  sharing a `venue_micros` key are scheduled together; that is not evidence they depict the
  same moment. A tick is a scheduling unit.
- **A tick's `alignment` covers its contributors only, and is not the session's alignment.**
  A tick in which the one unaligned camera happens not to contribute reports the *better*
  alignment of those that did. The session-level alignment — the worst across every
  registered stream, contributing or not — is recorded separately, and is the figure to read
  when asking how well this session's clocks are related at all.
- **Segment overlap within one camera cannot be fully verified.** A camera's source offsets
  are required to be strictly increasing, which rejects the obvious error of stacking two
  segments at the same instant. Whether segment N+1 actually begins after segment N *ends*
  is not checked, because it would require trusting the container's `frame_count`, which
  this design deliberately does not. An operator who declares overlapping offsets gets
  overlapping segments.
- **Fan-in cost grows with stream count.** Each tick does O(streams) work rather than an
  O(log streams) heap lookup, and tick count is itself O(streams), so total scheduling cost
  grows faster than linearly in camera count.

  *Methodology matters here and is stated because an earlier draft of this document
  published figures that were 4–5× optimistic:* they were measured through a test fake that
  pre-materialises its frames, which omits the per-peek `StreamFrame` construction that
  dominates real scheduling. The figures below were re-measured through a real cursor.
  Roughly **41,000 ticks/s at 1 stream** and **23,000 at 4**; at 40 streams, one minute of
  footage per camera costs about **16 s** of scheduling CPU.

  At realistic camera counts this remains orders of magnitude below detection cost and is
  genuinely negligible. At 40+ cameras it is still small *relative to detection* but no
  longer negligible in absolute terms. A heap-based merge is the obvious remedy if a
  deployment ever needs one; it was not built, because the simplest sufficiently robust
  design is the V1 rule. **No figure here was measured on real simultaneous multi-camera
  footage**, because none exists in this repository.

- **`venue inspect` artifact size grows as O(streams²).** Measured ~400 B/tick at 1 stream,
  ~3.1 KB at 40 and ~9.3 KB at 128 — and tick count also scales with stream count. At 40
  cameras over 12 hours that extrapolates to roughly **135 GB** of uncompressed JSONL, about
  97.5% of it the `absent` array. There is no tick cap, no sampling and no `--max-frames` on
  this command. "Reporting is streamed" is a statement about **memory**, not about artifact
  size. Treat long multi-camera inspections accordingly.

- **`--max-frames` does not apply to the `process()` path.** It is enforced in the
  single-source frame supply that `run()` drives. When a later milestone drives processors
  from a venue session, the flag will not cap anything unless that path enforces it.
- **`FpsMeter` is cosmetically misleading in a venue session.** It measures wall time between
  one camera's frames, which now includes other cameras' work. Display only; no measurement
  depends on it.
- **A mid-session source failure ends the session.** V0.4.0 fails fast, matching
  `FileVideoSource` and the validation runner. Tolerant degradation — a `FAILED` activity
  and continued operation with reduced coverage — is the live-deployment seam and is not
  built.
- **A container that misreports its own resolution is still mishandled, consistently.**
  Frame geometry comes from the container's declared resolution, as it did before V0.4.0.
  Where a container lies about it — rotation metadata reported pre-rotation is the common
  real case — zone polygons, the normalized projector and the ground-plane homography are
  all normalised against dimensions the detections did not come from.

  An interim revision of this milestone changed *one* of those four sites to use the decoded
  frame instead. That was withdrawn: it left zone labels computed in decoded space attached
  to behaviour signals computed in container space, which is worse than being wrong the same
  way everywhere. Correcting it properly means changing all four sites together — including
  `validation/`, which is frozen under active V0.3.6 validation — and is a bounded task for
  a later milestone, not a side effect of this one.

## Next milestone

Not yet specified. The layer above this one — Multi-Camera Association / Fusion and
temporary venue-local identity — is a **V1** capability and gets built when a bounded,
approved implementation task calls for it. When it does, it is validated on its own terms:
true associations, missed associations, **incorrect merges**, ambiguous cases,
duplicate-count suppression and provenance integrity — with false merges treated as the most
serious class.
