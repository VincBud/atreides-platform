# V0.4.8 — End-to-End Multi-Camera Validation Runner

**Status:** implemented · **Engineering milestone:** V0.4.8 ·
**Product generation:** V1 · **Not production ready**

## Purpose

V0.4.7 closed the last individual seam: every step from a decoded frame to a venue-local
subject now exists and is independently tested. Nothing drove them together. This milestone
adds one deterministic engineering harness that walks a configured venue session once,
through the *real* runtime, and writes what happened.

It is a **validation runner**, not a product runtime. It is not a service, not a deployment
target, not a dashboard, and it makes no accuracy claim about anything. It adds **no new
perception, association, fusion, identity or occupancy logic** — every number it reports was
produced by the layer that owns that number.

The harness answers one question: *does the committed stack actually run end to end, on more
than one camera, deterministically, and does it tell the truth about what it did?*

## Architectural position

```text
services/vision/src/atreides_vision/
└── venue_validation/
    ├── __init__.py       # public surface
    ├── config.py         # VenueValidationConfig, VenueValidationCameraConfig
    ├── models.py         # VenueValidationSummary, VenueValidationStreamSummary
    ├── reporting.py      # summary artifact, schema_version 0.4.8
    └── runner.py         # run_venue_validation(...)
```

`venue_validation` is a **composition root**. It sits above everything and is imported by
nothing but `cli.py`. Its allowed reach is wide by nature — wiring layers together is its
entire job — and is bounded in the other direction by a boundary test: no layer beneath it
may import it, and it may not reach into a risk engine, a decision engine, a dashboard, an
API surface, a model library, or anything ReID/embedding/biometric shaped.

Layer ownership is preserved exactly:

| Owner | Responsibility |
| --- | --- |
| `video/`, `detection/`, `tracking/` | frames, detections, camera-local tracks |
| `calibration/`, `behavior/` | projection and calibrated camera-local runtime truth |
| `venue/` (V0.4.0) | stream identity, venue timebase, tick schedule, source lifecycle |
| `track_observation_adapter` (V0.4.7) | camera runtime → `TrackObservation` |
| `venue_pipeline` (V0.4.4) | association, fusion, venue-local identity runtime state |
| `occupancy/` (V0.4.6) | current venue occupancy and duplicate suppression |
| `venue_pipeline_reporting` / `occupancy/reporting` | versioned JSONL |
| **`venue_validation` (V0.4.8)** | **orchestration and artifact lifecycle only** |

## Public API

```python
def run_venue_validation(
    config: VenueValidationConfig,
    *,
    detector: PersonDetector,
    tracker_factory: Callable[[TrackerConfig], MultiObjectTracker],
    source_factory: Callable[[VenueStreamEntry], VideoSource] = open_stream_source,
) -> VenueValidationSummary: ...
```

One call is one session. The detector is shared across cameras because detection is
per-frame and stateless; the tracker arrives as a **factory** because tracking is not — a
tracker shared between two cameras would continue one camera's track ids onto another
camera's people, which is precisely the identity error the architecture forbids.
`source_factory` exists so a test proving the venue loop's timing and ordering does not need
a decodable H.264 file, model weights or a GPU; it defaults to a real file source.

## End-to-end runtime flow

```text
VenueSessionManifest (V0.4.0)
  └─ per camera, per source epoch:
       source_factory(entry)                    -> VideoSource
       VenueTimebase.register(stream, ...)      -> venue time for that stream
       VideoSourceCursor(stream, source, ...)
       BehaviorAnalyzer + GroundPlaneProjector + CalibrationIntegrityGuard
       VideoProcessor(detector, tracker, config, behavior_analyzer, integrity_guard)

VenueSession(session_id, timebase, cursors).ticks()          # one single pass
  for tick in ticks:                                          # canonical contributions
      for frame in tick.contributions:                        # StreamFrame
          VideoProcessor.process(frame, sink)                 # detect → track → behaviour
          behavior.latest_frame.snapshots                     # ← the V0.4.7 input seam
          build_track_observation(snapshot, frame,
                                  calibration=..., integrity_guard=...)
      result   = VenuePipeline.process_instant(tick.venue_seconds, observations)
      snapshot = compute_occupancy(result, pipeline.registry)
      association_writer.write_instant(result, pipeline.registry)   # V0.4.5
      occupancy_writer.write_snapshot(snapshot)                     # V0.4.6

VideoProcessor.finish() per stream, all sources and writers released
write_validation_summary(...)                                      # only on success
```

### The camera-local runtime → adapter seam

The single design question this milestone had to answer was whether the committed
camera-local processor exposes enough runtime state to build a `TrackObservation` without
duplicating processing logic. It does, and **no lower layer was modified**.

`VideoProcessor.process(frame, sink)` drives the injected `BehaviorAnalyzer` synchronously.
Immediately after that call returns, the analyzer's public `latest_frame` property *is* that
frame's `BehaviorFrame`, whose `snapshots` are that frame's `BehaviorSubjectSnapshot`s. The
runner constructed the projector, the integrity guard and the analyzer itself, so all four
inputs `build_track_observation` requires are in hand at the composition root:

| Adapter input | Where the runner gets it |
| --- | --- |
| `snapshot` | `behavior.latest_frame.snapshots`, immediately after `process()` |
| `frame` | the `StreamFrame` the venue tick just handed to `process()` |
| `calibration` | the `GroundPlaneProjector` the runner built for that stream, or `None` |
| `integrity_guard` | the `CalibrationIntegrityGuard` the runner injected, or `None` |

The runner **never constructs a `TrackObservation`, `CameraSpatialContext`, `VenueRegion` or
`VenuePosition` itself** — a boundary test asserts this by AST inspection, and asserts
`build_track_observation` is actually called. The adapter's own consistency checks reject a
snapshot paired with a frame that did not produce it.

## Configuration contract

No parallel camera manifest was invented. The existing V0.4.0 `VenueSessionManifest`
(`manifest_version` `0.4.0`, `config/venue/example.json`) remains the authority on which
cameras and streams exist, their epochs, declared frame rates and declared offsets.
`VenueValidationConfig` adds only what a manifest cannot carry:

```python
VenueValidationConfig(
    manifest: VenueSessionManifest,
    output_dir: Path,
    cameras: tuple[VenueValidationCameraConfig, ...] = (),
    detector: DetectorConfig = DetectorConfig(),
    tracker: Tracker = DEFAULT_TRACKER,
    identity: VenueIdentityConfig = VenueIdentityConfig(),
    deduplicate_detections: bool = True,
)

VenueValidationCameraConfig(
    camera_id: str,
    calibration_path: Path | None = None,
    integrity_reference_path: Path | None = None,
    integrity_report_only: bool = False,
)
```

- `cameras` need **not** cover every manifest camera. An unconfigured camera runs
  uncalibrated and unmonitored; it still contributes tracks and occupancy.
- A camera named here but absent from the manifest, or named twice, is a `ConfigurationError`
  at construction.
- **Association gating and decision thresholds are deliberately not exposed.** Retuning them
  from a validation harness is exactly the frozen-scope violation the project forbids.
- Nothing encodes a camera count, a quadrant scheme, a naming convention, a coverage area,
  an overlap assumption or a topology. One camera, two, or arbitrary N are the same path.

Artifact paths derive from `output_dir` with fixed filenames:
`venue_pipeline_report.jsonl`, `occupancy_report.jsonl`, `venue_validation_summary.json`.

## Camera and source lifecycle

Sources open once per `(camera_id, stream_epoch)` and are registered with a single
`VenueTimebase`; the schedule is walked by a single `VenueSession.ticks()` pass. **No second
scheduler exists.** Everything V0.4.0 established is preserved unchanged:

- Deterministic venue time, with explicit `TimeUncertainty` on every frame.
- `stream_epoch` is the source's position in its camera's list and nothing else —
  never derived from a frame index, timestamp, filename or retry count.
- Cameras may have different frame rates, start at different offsets and end at different
  times. A stream that has ended contributes no further frames and **fabricates nothing**;
  a stream with zero frames is a supported case and the session continues without it.
- Ordering is canonical throughout: `VenueTick.contributions` are already canonically
  ordered, and every runner-side iteration over streams sorts by `stream_sort_key`. Manifest
  camera order never reaches an artifact.
- No wall-clock synchronisation anywhere.
- Source failure is **fail-fast**, exactly as V0.4.0 defines it. Errors propagate unchanged.

Every source, sink and JSONL writer is held in one `ExitStack`, so all of them are released
on the success path and on the failure path alike.

## Venue time and `stream_epoch`

`tick.venue_seconds` is passed verbatim to `VenuePipeline.process_instant`. Each
`TrackObservation` carries its own `venue_seconds`, `stream_epoch`, timing basis and timing
half-width from the `StreamFrame` the adapter received. The runner computes no time of its
own, applies no smoothing, and never substitutes a value it could not read. When a session's
alignment is `NOT_ESTABLISHED` — because no operator declared offsets — association's
`VENUE_TIME_NOT_ESTABLISHED` hard gate refuses comparison, and observations report
`NOT_COMPARABLE`. That is the correct output, not a degraded one.

## Calibration and trust behaviour

The harness supports all four camera states truthfully, and never converts a missing input
into a fabricated one:

| Camera state | Runner behaviour | Association effect |
| --- | --- | --- |
| Calibrated, integrity reference given, monitor consistent | `GroundPlaneProjector` + guard injected; adapter reports `VERIFIED` | eligible for comparison |
| Calibrated, no integrity reference | projector injected, guard `None`; adapter reports `UNVERIFIED` | as the gates already define |
| Calibrated, drift detected / metric output withheld | guard reports it; adapter reports `UNTRUSTED` | `CAMERA_GEOMETRY_UNTRUSTED` refuses the pair |
| Uncalibrated | normalized-frame projector, no ground-plane metres | `NOT_GROUND_PLANE_METRES` → `NOT_COMPARABLE` |

Guarded is the integrity default; `integrity_report_only` is opt-in, per camera, and is only
accepted alongside a reference. **No metre, m/s or venue coordinate is ever derived for an
uncalibrated camera**, and the runner never invents a homography, a venue frame or a surface
id to make a session comparable.

## Summary metrics

`venue_validation_summary.json` carries `schema_version`, the two artifact **filenames**
(never absolute paths), an execution-only note, and:

- `session_id`, `ground_truth` (always `NOT_ANNOTATED`)
- `configured_camera_count`, `configured_stream_count`, `contributing_camera_ids`,
  `zero_frame_streams`
- per-stream: `camera_id`, `stream_epoch`, `fps`, `fps_source`, `frames_processed`,
  `observations_emitted`, `calibrated`, `integrity_monitored`
- `venue_instants`, `source_frames_processed`, `observations_emitted`
- `association_outcome_counts` — every `AssociationOutcome` member, zero-filled
- `integration_outcome_counts` — every `IntegrationOutcome` member, zero-filled
- `venue_subjects_created`, `venue_subjects_current`
- `occupancy`: `snapshots`, `min_current`, `max_current`, `mean_current`,
  `suppressed_duplicates`
- `venue_time`: `first_seconds`, `last_seconds`, `span_seconds`, `session_time_alignment`

**These are execution statistics and nothing else.** There is no precision, no recall, no
false-merge rate, no missed-association rate, no occupancy error and no id-switch figure —
because no run this harness performs is annotated, and a zero must never stand in for a
measurement nobody made. The artifact says so in its own `note`, because a summary travels
further than the document explaining it.

## Determinism

Equivalent configured inputs produce byte-identical artifacts. Guaranteed by:

- canonical stream ordering everywhere (`stream_sort_key`), so manifest camera order is
  irrelevant — a test runs the same session with the cameras listed both ways and compares
  bytes;
- `VenueTick.contributions` already canonically ordered by the venue layer;
- no dict or set iteration order reaching an artifact;
- no wall-clock timestamp, run id, process id, hostname or absolute path in any artifact;
- fixed rounding precision for seconds and frame rates;
- no unseeded randomness anywhere in the measurement path.

Wall-clock performance measurement is simply absent rather than fenced off — it is not part
of any artifact contract.

## Failure and resource cleanup

- V0.4.0 fail-fast source semantics are preserved; underlying errors propagate unchanged.
- All sources, sinks and writers live in one `ExitStack` and are released on failure.
- **A failed run writes no summary.** `write_validation_summary` is called only after the
  stack has closed cleanly, so a summary on disk means the run it describes completed. An
  empty, successful-looking summary would be worse than no summary at all; no `status=FAILED`
  document, no zero-filled placeholder, no fabricated metrics.
- Already-flushed JSONL lines remain on disk with their writers' own semantics. There is no
  checkpoint or recovery mechanism, deliberately.

## Single-camera and zero-frame behaviour

A single-camera session is the same code path, not a mode: sources open, the schedule runs,
observations are adapted and fed to `VenuePipeline` exactly as with N cameras. With one
camera there is simply no cross-camera pair to assess, so no association decisions are
produced, nothing is suppressed, and occupancy equals the count of currently active
camera-local tracks. A zero-frame stream is reported in `zero_frame_streams` with
`frames_processed: 0` and the session continues.

## CLI surface

The existing `venue` command group provided a natural seam, so a diagnostic entry point was
added beside `venue inspect`:

```bash
atreides-vision venue validate \
  --manifest config/venue/example.json \
  --output-dir artifacts/venue_validation \
  --calibration cam_north=config/calibration.cam_north.json \
  --calibration-reference cam_north=data/input/venue/cam_north_ref.png \
  [--integrity-report-only] [--confidence 0.5] [--device auto] [--tracker bytetrack] [-v]
```

`--calibration` and `--calibration-reference` take repeatable `CAMERA=PATH` arguments, so no
camera count or naming convention is baked into the CLI. A reference without a calibration
for the same camera is refused: there is no metric claim to invalidate on an uncalibrated
camera. Business logic stays out of `cli.py` — the command loads the manifest, builds a
`VenueValidationConfig`, constructs the detector, calls `run_venue_validation`, logs the
artifact paths and the `NOT_ANNOTATED` disclaimer, and returns. It exits non-zero on any
`AtreidesVisionError`. **This is an engineering diagnostic, not a production command.**

## What existing validation data can and cannot prove

`config/validation/v0.3.6.json` holds four real CCTV clips. Each is *different footage from a
different camera*, none is calibrated, and none was recorded as a synchronised view of a
shared scene. Running them through this harness as a multi-camera session would be
mechanically possible and **evidentially worthless for association**.

Such a run **can** demonstrate: that the runner executes end to end on real footage; source
lifecycle and cleanup; venue scheduling across heterogeneous frame rates and durations; that
uncalibrated, unaligned cameras produce `NOT_COMPARABLE` rather than invented geometry; that
artifacts are produced and are deterministic.

It **cannot** demonstrate: cross-camera association accuracy, false-merge rate,
missed-association rate, duplicate-suppression accuracy, or venue occupancy accuracy. Two
unrelated clips contain no true cross-camera correspondence at all, so a run that merges
nothing proves nothing about merging, and a run that merged something would be an error, not
a result. No such run may be reported as association validation.

## Validation status

Synthetic and unit only. The tests use fake detector, tracker and video sources — no weights,
no network, no GPU — and drive the **real** `VideoProcessor`, `BehaviorAnalyzer`,
`GroundPlaneProjector`, `CalibrationIntegrityGuard`, `VenueSession`, adapter, `VenuePipeline`,
occupancy analyzer and both JSONL writers. They cover single-camera, two-camera, manifest
ordering, differing frame rates, ended and zero-frame streams, stream epochs, declared and
undeclared alignment, calibrated/uncalibrated/untrusted geometry, artifact schemas, summary
consistency, byte-identical replay, adapter-only observation construction, resource release
on success and on failure, and fail-fast mid-session source failure.

**Execution success on synthetic or unannotated footage is not association accuracy
validation.** This milestone establishes that the stack runs and reports truthfully. It
establishes nothing about how well it associates real people across real cameras.

## Explicitly out of scope

- No annotation tooling, no accuracy scoring, no precision/recall, no false-merge or
  occupancy-error metric against human labels.
- No automatic threshold tuning; no new association, fusion, identity or occupancy logic.
- No ReID, embeddings, appearance templates, biometrics or persistent identity. Venue-local
  identity remains session-scoped and is discarded when the run ends.
- No entry/exit counting or cumulative visitor totals.
- No Risk/Decision Engine, no dashboard, no deployment service, no distributed processing or
  GPU scheduling.
- No V2 low-light/strobe work, no V3 sensor or hardware assumptions.

## Known limitations

- Annotated frames produced by the camera-local processor are discarded (the sink writes to
  nothing). The harness validates the measurement path, not rendering; per-camera MP4 output
  would dominate a run's cost with output nobody reads.
- A failed run leaves the two streaming artifacts partially written, with no marker in them
  saying the run did not complete. The absence of the summary file is the signal.
- The summary reports `venue_subjects_created` as the registry's total subject count at the
  end of the run; with bounded eviction over a long session that is a count of *retained*
  subjects, not a lifetime total. It is not a cumulative visitor figure and must not be read
  as one.
- No repository-committed multi-camera fixture of genuinely overlapping real footage exists,
  so no real association claim can currently be made at all.

## Next seam: V0.4.9 Real Multi-Camera Ground-Truth Validation

Everything above measures execution. The next milestone is the one that measures
correctness: genuinely overlapping multi-camera footage, human-annotated cross-camera
correspondence, and association evaluated on its own terms — with **false merges the most
serious class**, missed associations reported separately, and `NOT_ANNOTATED` still emitted
wherever a human has not actually annotated.
