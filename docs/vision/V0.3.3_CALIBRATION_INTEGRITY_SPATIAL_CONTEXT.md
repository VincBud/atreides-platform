# V0.3.3 — Calibration Integrity & Spatial Context

**Status:** implemented · **Substep:** V0.3.3 of V0.3 · **Not production ready**

## Purpose

Three bounded goals.

**A. Calibration integrity.** V0.3.1 assumed the camera never moves; V0.3.2 said
so in the documentation and did nothing about it. A nudged, rotated, re-zoomed
or re-cropped camera keeps producing confident metre values from a premise that
is no longer true, and nothing downstream can notice. V0.3.3 detects that and
stops it.

**B. Spatial context.** Zone membership now travels to behaviour output as
neutral context, so a consumer can see *camera_A / track_17 at (8.4 m, 12.1 m)
in the dancefloor zone* — without the behaviour layer becoming a zone engine.

**C. Output volume control.** Deterministic emission sampling and gzip
compression, with **analysis unchanged**: every frame is still analysed in full.

## Architecture

```text
                       ┌─ zone_ids (opaque labels) ─┐
video → detect → track ┤                            ├→ BehaviorAnalyzer → BehaviorFrame
                       └─ MotionProjector ──────────┘                          │
                                                                               ▼
current frame → CalibrationIntegrityGuard → IntegrityAssessment      BehaviorEmissionPolicy
                  (monitor measures,               │                           │
                   policy decides)                 ▼                           ▼
                            metric_output_allowed ────────────────→ JsonlBehaviorWriter
                                                                    (.jsonl or .jsonl.gz)
```

```text
calibration/integrity/
├── models.py        # IntegrityState, RegistrationEvidence, metrics, assessment
├── config.py        # thresholds, cadence, policy mode
├── registration.py  # FrameRegistrationBackend + ORB — the only OpenCV here
├── monitor.py       # evidence → state, on a schedule (MEASURES)
└── policy.py        # CalibrationIntegrityGuard (DECIDES)
```

Layering rules preserved:

- OpenCV feature APIs appear in `registration.py` only. Nothing above it sees a
  keypoint; everything consumes the plain `RegistrationEvidence` value object.
- The **behaviour package still does not import the calibration package** — nor
  the zone package. A test parses every behaviour module's imports to enforce it.
  Integrity findings reach the writer through an `IntegrityFinding` Protocol.
- `VideoProcessor` does no feature matching, holds no thresholds and applies no
  emission arithmetic. It relays a finding and honours one boolean.

`IntervalSampler` (new, in `sampling.py`) is the one scheduling primitive shared
by zone metrics, behaviour emission and integrity cadence. `MetricsSampler` is
now a thin subclass of it, so V0.2 behaviour is unchanged.

## Integrity versus accuracy

**This is the most important distinction in the milestone.**

| The monitor proves | The monitor does **not** prove |
|---|---|
| The current frame registers against the reference frame | That the calibration's metres are correct |
| The camera viewpoint appears unchanged | That reference points were measured accurately |
| A *precondition* for trusting metric output still holds | Any real-world accuracy figure |

A calibration whose floor points were measured against the wrong spots is
perfectly `CONSISTENT` — the camera has not moved, it is simply wrong. A
perfectly measured calibration becomes untrustworthy the moment the camera is
nudged, which is what `DRIFT_DETECTED` reports. Only physical measurement
establishes accuracy; this establishes that its precondition survives.

State names reflect that: there is no `ACCURATE`, `SAFE` or `PRODUCTION_READY`,
and a test asserts none is ever introduced.

## Reference frame

Correspondence coordinates alone cannot detect camera movement — they describe
where points *should* be, not what the camera currently sees. Integrity
therefore requires a **reference image** captured from the calibrated camera
geometry:

```text
calibration authored + reference frame captured  →  integrity reference
later runtime frame                              →  compared against it
```

Supplied by path (`--calibration-reference`), never embedded in calibration
JSON: image binaries do not belong in a config file, and machine-specific paths
do not belong in a committed example. The path is recorded as `reference_id` in
output records so a finding can be traced to what it was compared against.

## Registration

Default backend: **ORB keypoints → Hamming ratio-tested matching → RANSAC
homography → inlier statistics.** ORB ships with OpenCV, which is already a
dependency, so no package was added. It is not a neural model and needs no
weights.

The registration target is the **static scene** — door frames, bar edges, floor
markings. No face, body or person feature is computed anywhere. Moving people
are simply the minority of the frame that fails to agree with the fit, which is
how a robust estimator is meant to treat them.

Determinism: `cv2.setRNGSeed` is called immediately before each RANSAC fit, so
the same frame pair always yields the same verdict. That is process-global state
this codebase otherwise avoids; it is accepted because a non-reproducible
integrity verdict would be worse, and it is confined to one call site.

## Metrics

| Metric | Meaning |
|---|---|
| `reference_keypoints` / `current_keypoints` | Scene features found in each frame |
| `matches` | Candidate descriptor matches |
| `inliers` | Matches agreeing with the fitted transform |
| `inlier_ratio` | Share of matches the fit explains |
| `mean_reprojection_error_px` | Fit residual, in reference pixels |
| `normalized_drift` | **Primary drift metric.** Mean corner displacement as a fraction of the frame diagonal |
| `max_normalized_drift` | Worst single corner, same units |

**Drift is never measured in pixels.** The reference frame's four corners are
pushed through the fitted transform, then *both sides are normalized by their own
frame size* before comparison. Two consequences:

- A 40-pixel shift on 1080p and a 9-pixel shift on 384×288 score the same, so
  one threshold serves every camera.
- A **proportional decode resize scores zero** — the corners land at the same
  relative positions even though every pixel coordinate doubled. The V0.3.1
  resolution contract holds at this layer.

## States

| State | Meaning |
|---|---|
| `UNCHECKED` | No check has run yet — before the first, or with monitoring off |
| `CONSISTENT` | Geometry matches the reference. The viewpoint appears unchanged |
| `DRIFT_DETECTED` | The fit is sound and the geometry moved past the limit |
| `INSUFFICIENT_EVIDENCE` | The check could not conclude — too little texture, too few matches, an unstable fit |

**Evidence sufficiency is judged before drift.** A huge apparent shift derived
from six matches is a guess, not a finding, so it reports
`INSUFFICIENT_EVIDENCE`. And `INSUFFICIENT_EVIDENCE` is never collapsed into
`CONSISTENT`: "could not tell" and "nothing changed" are different facts, and
conflating them would be the most dangerous thing this module could do. A test
asserts a blank frame is never reported as consistent.

## Development thresholds

| Setting | Default | Unit |
|---|---|---|
| `minimum_keypoints` | `40` | features, per frame |
| `minimum_matches` | `20` | candidate matches |
| `minimum_inliers` | `12` | matches |
| `minimum_inlier_ratio` | `0.30` | fraction |
| `maximum_reprojection_error_px` | `6.0` | reference pixels |
| `maximum_normalized_drift` | `0.02` | fraction of frame diagonal |
| `maximum_max_normalized_drift` | `0.035` | fraction of frame diagonal |
| `check_interval_seconds` | `5.0` | seconds of source time |
| `policy_mode` | `GUARDED` | — |

> **DEVELOPMENT defaults.** No measurement backs them. They have not been
> validated against real venue footage, and **no false-positive or
> false-negative rate is known.**

`0.02` of the diagonal is roughly 44 px on 1080p and 9 px on 384×288 — the same
relative movement on both. **No threshold encodes a physical size**, so a camera
covering a doorway and one covering a festival field share one configuration.

Cadence is time-based rather than frame-based, so it does not change with source
frame rate. Feature matching costs ~20 ms per check and camera movement happens
on a scale of seconds, so running it every frame would be both ruinous and
pointless.

## Runtime fail-safe policy

Measurement and consequence are separate classes: the monitor measures, the
guard decides.

| State | Metric observations | Recorded? |
|---|---|---|
| `UNCHECKED` | continue | — (no check has run) |
| `CONSISTENT` | continue | yes, as a `calibration_integrity` record |
| `DRIFT_DETECTED` (guarded, default) | **stop, for the rest of the run** | yes, with `metric_output_allowed: false` |
| `DRIFT_DETECTED` (report-only) | continue | yes, plus a loud warning |
| `INSUFFICIENT_EVIDENCE` | continue | yes — never silent |

**Suppression does not lift.** Once drift is detected in guarded mode, metric
observations stop permanently, even if a later check comes back consistent. A
camera that moved, was checked, and appears to match again has still been
through an unobserved change; treating the intervening measurements as fine
because the last check passed would be exactly the silent trust this guard
exists to prevent. Re-establishing trust means re-calibrating — a deliberate
operator action.

Suppression stops *serialisation*, not analysis: the run continues, the video is
still written, and the stream carries the integrity record explaining the gap so
a consumer can tell suppression from an empty scene.

`--integrity-report-only` exists for diagnosing the monitor itself. It is never
silent.

**Detection is not recalibration.** Nothing is automatically altered —
homography, correspondences, config and venue coordinates are untouched.

## CLI

```bash
# Metric behaviour with camera-drift monitoring
atreides-vision run \
  --input data/input/clip.mp4 \
  --output artifacts/tracked.mp4 \
  --behavior-output artifacts/behavior.jsonl.gz \
  --calibration config/calibration.json \
  --calibration-reference data/input/reference.png \
  --behavior-output-interval 0.5

# Standalone integrity check, no detector or tracker involved
atreides-vision calibration integrity \
  --calibration config/calibration.json \
  --reference reference.png \
  --current current.png \
  --output artifacts/integrity.png
```

| Flag | Default | Meaning |
|---|---|---|
| `--calibration-reference` | off | Reference frame; enables monitoring. Requires `--calibration` |
| `--integrity-report-only` | off | Keep emitting after drift. Requires `--calibration-reference` |
| `--behavior-output-interval` | off (every frame) | Seconds of source time between emitted snapshots |

Integrity applies only where a calibration exists — normalized-only behaviour
makes no metric claim to invalidate, and asking for it there is rejected rather
than silently ignored. A missing or unreadable reference fails **before the
detector loads**, so monitoring is never quietly skipped on a run that asked for
it.

### `calibration integrity` output

```text
Calibration: config/calibration.example.json (camera 'cam_01')
Reference:   ref.png at 1920x1080
Current:     moved.png at 1920x1080
State:       drift_detected
Reason:      the view has moved: mean corner displacement 3.19% of the frame diagonal exceeds 2.00%
Features:    reference 2004, current 2010
Matching:    1041 candidates, 832 inliers (80%)
Fit:         mean residual 0.57 px
Drift:       mean 3.189% of the frame diagonal, worst corner 3.201%
Note:        this compares image geometry against the reference. It says whether the camera
             view has moved, not whether the calibration's metres are physically correct —
             only measurement on the floor can establish that.
```

No GOOD/BAD/SAFE verdict, and no accuracy claim.

### Visual diagnostic

`--output` draws the reference frame's outline where it now lands in the current
view. If the camera has not moved the outline hugs the frame edges; if it has,
the outline visibly slides, rotates or shrinks, and that gap **is** the drift
being reported. State, inlier counts and drift are printed on the image.

Diagnostic only: no GUI, no editing, no automatic recalibration.

## Zone / spatial context

`ZoneAnalyzer` gained one read-only property, `zone_ids_by_track`. The processor
passes it to `BehaviorAnalyzer.update(zone_ids_by_track=...)` — a parameter that
has existed since V0.3.0 and was simply never populated.

The behaviour layer receives **opaque strings**. It never sees a polygon, never
learns what a zone is, and never imports the zone package.

**Zones remain camera-local image-space regions.** V0.3.3 passes a *label*, not
geometry. A zone id attached to a metric position does not make the polygon
venue geometry, and no polygon was converted to metres — there is not enough
information to do that correctly, and doing it anyway would be exactly the kind
of silent wrongness this milestone is about. Venue-level ground-plane zones are
a separate future evolution.

Overlapping zones are represented faithfully as an ordered tuple, in
configuration order. A track in no zone is **absent from the mapping** rather
than present with an `"unknown"` label — absence already expresses it.

Zone metrics themselves are untouched.

## Behaviour output contract

**Schema version: `0.3.2` → `0.3.3`.**

The bump exists for one reason: a third `record_type` now appears.

```json
{"record_type":"calibration_integrity","schema_version":"0.3.3","camera_id":"cam_01",
 "state":"drift_detected","frame_index":251,"timestamp_seconds":10.0,
 "reason":"the view has moved: mean corner displacement 8.6% of the frame diagonal exceeds 2.00%",
 "reference_id":"reference.png",
 "metrics":{"reference_keypoints":1204,"current_keypoints":1198,"matches":812,"inliers":655,
            "inlier_ratio":0.8067,"mean_reprojection_error_px":0.53,
            "normalized_drift":0.086,"max_normalized_drift":0.0861},
 "metric_output_allowed":false,"venue_id":"example_venue","surface_id":"ground"}
```

Observation records gain the already-contracted optional `zone_ids` field, now
actually populated:

```json
{"record_type":"observation","schema_version":"0.3.3","camera_id":"cam_01",
 "frame_index":123,"timestamp_seconds":4.92,"subject":{"track_id":17},
 "position":{"x":8.4,"y":12.1,"space":"ground_plane_metres","unit":"m"},
 "signals":[{"type":"speed","value":1.24,"unit":"m/s","quality":1.0}],
 "venue_id":"example_venue","surface_id":"ground","zone_ids":["dancefloor"]}
```

### Compatibility decision

**Observation and run-metadata records are structurally unchanged.** A 0.3.2
consumer reading those keeps working, and a regression test pins the observation
keys to prove it.

The version was still bumped because a consumer that asserts on the *set* of
record types will now encounter one it does not know. A new line type on the
wire is a contract change worth announcing rather than slipping through. It was
not bumped for the `zone_ids` field alone — that field was already part of the
0.3.2 contract and merely went from never-populated to sometimes-populated.

`zone_ids` was kept flat rather than nested under a new `spatial_context`
object: the field already existed, and wrapping one key in an object is churn
without benefit.

Integrity records are **camera- and run-level**. They carry no subject, no track
id and no person-level field, and a test asserts it.

## Output volume control

| Control | Default | Effect |
|---|---|---|
| `--behavior-output-interval SECONDS` | off | At most one emitted snapshot per interval of source time |
| `.jsonl.gz` output path | off | Streaming gzip compression |

**Analysis is never sampled.** The emission policy lives in the *writer*, after
the analyzer has already ingested the frame. `frames_analysed` and
`frames_written` are both exposed and diverge whenever an interval is set —
directly demonstrating that history is complete while output is thinned. Speed
and acceleration are therefore identical whether the file holds every frame or
one per second.

Sampling is per frame, so a frame is never half-written and subject ordering
stays deterministic. The first analysed frame is always emitted, so a run
shorter than one interval still produces observations. Run metadata and
integrity records are **never** suppressed — a missing integrity record would
leave a consumer unable to explain a gap.

Compression is chosen by the `.gz` suffix (one visible convention, no flag to
lose), overridable explicitly. It streams: each write is compressed into the
file, so memory does not grow with run length, and an interrupted run still
leaves a valid gzip stream.

## Multi-camera boundary

Unchanged and extended. Subject identity remains `camera_id + track_id`, and
**calibration integrity is per camera**: one camera may be `DRIFT_DETECTED`
while another in the same venue is `CONSISTENT`, with separate suppression
counts. Nothing is shared globally.

Two cameras are never merged because they share a track id, a position, a zone,
a timestamp or a calibration surface. **Spatial context is context, not
identity.**

Not implemented: ReID, appearance embeddings, venue-person ids, persistent
identity, cross-camera matching or fusion.

## Privacy boundary

Calibration integrity operates on scene geometry; zone context is spatial
metadata. Neither classifies a person. No facial recognition, body embeddings,
biometric identification, aggression/intoxication/distress detection,
suspicious-person labels, risk scores or automated intervention decisions were
added, and no new semantic person label exists anywhere in V0.3.3.

## Synthetic validation

All deterministic, from seeded imagery. Measured with default thresholds:

| Scenario | Result | Drift |
|---|---|---|
| Identical frame | `CONSISTENT` | 0.000% |
| Proportional resize ×0.5 / ×2 | `CONSISTENT` | 0.089% / 0.108% |
| Sensor noise | `CONSISTENT` | 0.003% |
| Brightness shift | `CONSISTENT` | — |
| **Moving foreground, stable background** | `CONSISTENT` | 0.001% |
| Translation 25 px | `DRIFT_DETECTED` | 2.67% |
| Rotation 4° | `DRIFT_DETECTED` | 4.59% |
| Zoom ×1.12 | `DRIFT_DETECTED` | 5.98% |
| Crop 12% and rescale | `DRIFT_DETECTED` | 15.69% |
| Perspective warp | `DRIFT_DETECTED` | 2.15% |
| Blank / low-texture frame | `INSUFFICIENT_EVIDENCE` | n/a |

The foreground case uses opaque blocks standing in front of an unchanged scene
and moving between frames — the everyday venue situation, which must not read as
camera movement. Robustness is claimed only to the degree these tests support:
**moderate** foreground occlusion with ample stable background.

## Real-world validation limitation

**No metre ground truth exists for the downloaded CCTV footage**, so V0.3.3
claims no physical accuracy, and no validated false-positive or false-negative
rate for drift detection. Every number above comes from synthetic geometry with
a known analytic answer. Real footage can demonstrate feature availability,
runtime stability and output volume — not measurement accuracy.

## Performance

Fake detector and tracker, deterministic synthetic input, **detector inference
excluded**. 500 frames, 8 people/frame, 960×540, median of 5 interleaved runs.

| Mode | ms/frame | vs baseline | Output size |
|---|---|---|---|
| Baseline (every frame, plain) | 0.507 | — | 1844 KiB |
| Sampled (0.5 s) | 0.408 | −0.098 | 146 KiB (**−92%**) |
| gzip | 0.497 | −0.010 | 37 KiB (**−98%**) |
| Integrity (5 s cadence) | 0.676 | **+0.169** | 1846 KiB |
| Sampled + gzip + integrity | 0.576 | +0.070 | 5 KiB (**−99.7%**) |

One ORB registration on 960×540 costs **19.7 ms**. At the default 5 s cadence
and 25 FPS that is one check per 125 frames, amortising to **0.158 ms/frame** —
which matches the measured +0.169 ms/frame.

Sampling makes runs *faster* by removing serialisation work.

**These figures say nothing about real-time capability.** They exclude the
detector, which dominates end-to-end cost by orders of magnitude, and use
synthetic frames.

## Known limitations

1. **No real-world validation** of drift detection: no measured false-positive
   or false-negative rate, and thresholds are unvalidated development values.
2. **Registration robustness is bounded by the tests.** Heavy occlusion, very
   low light, extreme motion blur and near-textureless venues are untested;
   those should surface as `INSUFFICIENT_EVIDENCE`, which is safe but leaves the
   run unverified.
3. **A drifted camera is detected, not corrected.** No recalibration, automatic
   or assisted.
4. **Drift between checks is invisible.** At a 5 s cadence, up to 5 s of
   observations from a moved camera can be emitted before the next check.
5. **Suppression is permanent within a run** by design, so a transient
   misdetection costs the remainder of the run's metric output.
6. **A slow drift may never trip the threshold**, since each check compares
   against the original reference but a gradual change can sit below the limit
   for a long time.
7. **Zones remain image-space.** Zone labels on metric positions are context
   only; there are no venue-space zones.
8. **`cv2.setRNGSeed` is process-global.** Concurrent registration in one
   process would interleave seeding.
9. **A single reference frame** represents the calibrated geometry. Lighting
   very different from it (day versus night) may reduce matches and yield
   `INSUFFICIENT_EVIDENCE`.
10. **The integrity overlay draws the fitted outline and summary only** — not
    individual matched features.
11. **Sampling is per frame, not per subject**, so a busy frame is emitted whole
    or not at all.
